在管理员导航下新增「渠道概览」，包含「渠道分析」「分组分析」「上游 Key 分析」「上游供应商分析」四个一级 Tab。产品目标是帮助管理员判断每天的流量由哪些渠道、采购凭据和供应商承接、用户体验是否稳定、费用如何分布、哪些组合产生毛利，以及异常由流量、价格、重试还是供应商变化引起。

## 4 收入 成本与毛利口径

### 4.1 原价的定义

将用户提出的「原价」定义为**基准计费金额 B**：按照调用当时冻结的模型价格、实际计费用量、命中档位、缓存与多模态规则、请求倍率及工具附加费用计算，尚未乘有效分组倍率的金额。

它是平台本次请求的基准计价金额，不自动等于供应商官网标价，也不自动等于供应商实际账单金额。成本倍率成立的业务前提，是该渠道采购价可以用同一计价基准乘一个比例表示。

基值分为模型主体、工具费用及其他费用明细，合计用于成本估算。表达式已经包含的请求倍率或费用不能重复叠乘。预扣估算基值与最终实际基值必须分别保存。

### 4.2 公式

设实际有效分组倍率为 G，本次选中 Key 与渠道共同解析的有效成本倍率为 K：

```text
理论计费额 = B × G
估算渠道成本 C = B × K
净计费额 R = 已确认结算计费额 − 对已确认收入的用户退款及冲减
估算计费毛利 P = R − 净估算渠道成本
估算计费毛利率 = P ÷ R，限 R > 0
```

单渠道、正常结算、没有退款和额外调整时，与用户的公式一致：

```text
毛利 = 原价 × 分组倍率 − 原价 × 成本倍率
```

实际页面以系统最终结算额 R 为准，以便与账务核对；理论额只用于解释价格、模拟和核验舍入差异。

例如同一币种下 B 为 100，G 为 1.2，K 为 0.7，计费额为 120，估算成本为 70，估算计费毛利为 50，毛利率为 41.67%。若 G 为 0 而成本仍为 70，则毛利为 −70，不能因为用户免费而抹去成本。

### 4.3 页面命名

主指标使用「净计费额」「估算成本」「估算计费毛利」「估算计费毛利率」。消费曲线默认显示净计费额，同时允许切换基准计费额、调用量和 tokens 等用量。

计费毛利衡量计量售价与采购估算的差额。它没有扣除服务器、支付手续费、税费、人工等，也没有完成充值赠送、折扣和套餐收入分摊，因此不能标为净利润或实收利润。

钱包与订阅分别展示。订阅部分称「订阅计量额」，允许查看其计量差额与成本，但不将计量额解释成每次调用产生的现金收入。全量合计始终保留「计费」限定。

### 4.4 多次尝试与退款

每个逻辑请求只确认一次最终计费收入；供应商成本按实际发生的尝试归属各渠道。若 A 失败后 B 成功，收入归最终服务渠道 B，A 保留其已知成本与失败记录。

每次尝试有自己的成本基值 B_i 和倍率 K_i，成本 C_i = B_i × K_i。模型映射、实际用量、图片数量、工具费用或插件定价不同时，不同尝试的基值可以不同。不能拿最终成功 B 渠道的基值去估算失败 A 渠道；缺少失败尝试的可靠用量或计价基值时，该次成本为未知。

失败不等于无成本。能够确认供应商未扣款才记零；能够获取已计费用量则估算或记录成本；不知道是否扣款的尝试标记「成本未知」。成功后发生的用户退款冲减收入，上游未退款则不冲减成本。

对重试请求，完整毛利公式为：

```text
请求毛利 = 请求净计费额 − 所有尝试的净成本之和
```

当任何相关尝试成本未知时，完整请求毛利显示未知。允许展示「已知成本」，但不能将收入减已知成本当成完整毛利。总毛利只在成本完整的请求集合上计算，并同时展示该集合的计费额、请求数及覆盖率。

各日、渠道、分组和导出均区分全量净计费额 R_all、已知成本 C_known，以及同一完整请求集合的净计费额 R_complete 和成本 C_complete。毛利为 R_complete − C_complete，毛利率仅除以 R_complete。完整性判断覆盖该请求全部尝试，包括当前渠道筛选之外的尝试；只筛选成功渠道不能隐去其他渠道的未知重试成本。渠道毛利只分配该渠道的收入与成本，不将整条请求毛利重复分配给各尝试渠道。

### 4.5 时间与金额精度

金额保存内部额度及统一核算币种等值，冻结额度换算尺度。首期建议使用 USD 为核算币种，展示币种转换仅用于显示并注明汇率来源与时间。计算使用足够精度的定点数或十进制数，汇总后按显示精度舍入，避免逐行显示金额累加造成误差。

调用与健康按请求或尝试开始时间形成时间桶；尚未结束的样本列为处理中，最终结果更新原始桶。经营按最终结算时间归属，后续退款和成本冲减在发生时记录独立调整事件，保留原事件关联，不直接覆盖历史记录。

异步任务的预扣显示为「待结算」，完成后确认最终计费额与成本。失败释放预扣只减少待结算金额，不冲减尚未确认的收入；已确认结算后发生的退款才冲减收入。完成前的资金差额只更新待结算，任务完成时确认最终实际额度一次，即使补扣差额为零也记录确认事实。任务跨日时分别显示提交、完成和结算时间。旧日志只能用于重建带来源标记的账务记录，不能把任务提交预扣与完成结算重复确认为收入。

## 5 渠道成本倍率管理

在渠道列表新增「成本倍率」列，展示数值、未配置状态和编辑入口。位置靠近额度或余额等经营字段，明确区别于路由权重。

| 配置项目 | 首期规则 |
| --- | --- |
| 成本倍率 | 可空、非负、有限数值；支持小数，建议最多六位小数 |
| 未配置 | 显示「未配置」，不默认为 0 或 1，不生成完整毛利 |
| 显式 0 | 表示确认上游免费，与未配置严格区分 |
| 大于 1 | 合法，表示采购成本高于基准；在示例中明确亏损可能 |
| 数值边界 | 服务端校验有限值、精度和安全范围，边界由金额计算能力确定 |
| 生效 | 首期保存后生效，仅影响之后发起的上游尝试 |
| 版本与审计 | 记录原值、新值、操作者、生效时间和变更说明 |
| 历史 | 保留过去的规则版本及本次调用快照，不随当前配置变化 |
| 批量修改 | 列出选中渠道、变更预览及逐项结果；失败项可重试 |

编辑入口打开共享 Dialog，使用支持小数与空值的表单。保存前展示公式和以示例基准金额计算的计费额、成本与毛利。渠道编辑抽屉在「其他设置」中增加「成本核算」区，与列表入口编辑同一份配置。

每次真正发送上游前冻结成本规则快照。切换渠道、切换模型或重试重新记录尝试快照；异步任务在提交时持久化快照，完成时沿用。请求进行中修改渠道成本，不能影响已经开始的尝试。

补充上游 Key 后，首期成本规则为「Key 明确覆盖 → 本次渠道默认 → 未配置」。Key 未覆盖时不写入复制出来的渠道倍率，保留继承关系；显式零值属于覆盖。记录实际使用的规则来源与版本。同一 Key 跨渠道继承出不同规则时，显示「继承多个渠道规则」，按各尝试计算，不平均倍率。供应商或账户默认价格作为后续扩展，不能与现有覆盖隐式叠乘。

渠道复制操作显式提供是否复制成本设置的选项，默认保留源设置并在复制预览中展示。渠道改名或删除后保留历史渠道 ID 与名称快照。

渠道倍率只参与经营估算。它不直接改变用户预扣、最终扣费、模型售价或路由权重。

后续扩展顺序为：渠道默认倍率、渠道模型覆盖倍率、独立采购价格或成本表达式、供应商实际账单。采购结构和平台基价不一致时，单倍率标记为近似；模型售价为零而上游收费时，首期必须允许标记「成本规则不足」，不能生成虚假的零成本。

| 事实 | 标识与计数规则 | 用途 |
| --- | --- | --- |
| 逻辑请求 | request_id；一次用户生成业务调用计一次；异步任务关联 task_id，不另加一次调用 | 用户需求、最终成功率、模型调用比例 |
| 上游尝试 | request_id + attempt_id；重试、换渠道分别计一次 | 渠道与组内健康、重试、供应商成本 |
| 账务事件 | 唯一事件 ID；结算、补扣、用户退款、上游退款分别记录方向 | 净计费额、成本调整、经营对账 |

异步任务的轮询和取结果不是用户模型调用，SSE 分块不是多个请求，任务补扣不是新增调用。多节点处理同一事件按事件 ID 去重。

同步调用、流式调用与异步任务分别展示健康。异步渠道的「提交接受率」衡量供应商是否接受任务，「任务最终成功率」衡量已结束任务是否产出有效结果，不能把提交 HTTP 200 当成生成成功。任务等待、执行和总耗时分别统计，不混入同步响应耗时或 TTFT；合计业务成功率只使用已结束业务调用，注明不同类型的组成。

任务被本地超时或轮询超限判定失败时，客户交付结果可为失败，但上游生成结果仍可能未知。分别保存客户结果、提交结果、任务观察结果与供应商终态证据，不自动记成供应商已证实失败；相关采购成本也不能因本地退款而归零。异步提交后的观察连接断开，不改变仍在执行的任务生成结果。

### 6.2 首期指标

| 指标 | 定义与限制 |
| --- | --- |
| 逻辑调用量 | 唯一请求或任务数；区分已完成、失败和处理中 |
| 上游尝试数 | 实际发起上游的次数；包含重试，不等于用户调用量 |
| 渠道执行成功率 | 渠道成功完成的有效尝试数 ÷ 该渠道终态可判定的已结束有效尝试数，同时展示终态覆盖 |
| 组内执行成功率 | 在该实际路由分组内成功完成的有效尝试数 ÷ 组内终态可判定的已结束有效尝试数，同时展示终态覆盖 |
| 请求最终成功率 | 经过所有重试后成功的逻辑请求数 ÷ 终态可判定的已结束有效逻辑请求数，同时展示未路由失败与终态覆盖 |
| 首次尝试成功率 | 首次尝试直接成功的请求数 ÷ 有首次有效尝试且已结束的请求数 |
| 重试请求率 | 发生第二次及后续尝试的请求数 ÷ 发起过上游的已结束请求数 |
| 重试恢复率 | 首次失败、经重试成功的请求数 ÷ 首次失败的已结束有效请求数 |
| 流式完整完成率 | 正常完成且无协议内失败的有效流式请求数 ÷ 已结束有效流式请求数 |
| TTFT P50 / P95 | 成功流式样本从发送到首个有效输出的耗时分位数，注明样本数 |
| 非流式耗时 P50 / P95 | 成功非流式样本从发送到完整响应的耗时分位数 |
| 超时率 / 上游限流率 | 对应失败尝试数 ÷ 已结束有效尝试数，说明超时与限流来源 |
| 净计费额 | 已确认最终计费减用户退款和冲减，按账务事件方向累计 |
| 成本与毛利 | 按成本来源与完整集合计算，不把未知当零 |
| 成本覆盖率 | 成本完整请求数 ÷ 纳入经营统计的请求数；金额覆盖以非负正向确认计费额为基数，退款后净额不作分母，基数为零时显示不适用 |

首期健康曲线以「执行成功率」为主，辅以 TTFT、耗时、超时率和流式完整率，不引入无法解释的综合健康分。渠道列表当前状态、最近短时健康与每日历史健康分别标明窗口。

客户端参数错误、用户本地鉴权失败、用户额度不足及客户端主动取消不计入供应商有效健康分母，分别展示计数。上游凭据失效、上游余额不足、供应商限流、上游响应超时及已确认上游连接故障计入渠道失败。网关内部异常、本地配置错误、整请求时间预算耗尽或无法归因的网络故障独立分类：体现为客户交付失败或未知，但不自动归责供应商。不能只按 HTTP 状态码排除全部 4xx，需按原因与责任归类。

HTTP 200 只是传输结果。流式中途失败、已确认协议要求的正常结束信号缺失、协议内失败、任务最终失败都必须在业务结果中体现。采集丢失或证据不足导致无法判定的请求为未知，不能自动归入成功，也不能用未知掩盖已有证据的协议失败。

成功率是可判定样本的成功率，需同时展示「终态可判定覆盖率」：有可判定终态的有效样本数，除以已结束或超出合理观察期限的有效样本数；正常处理中样本另列。不具备完整采集证据时标「未核验」。初始建议覆盖率至少 99% 且采集已核验才给健康正常结论，阈值可配置；覆盖不足时显示「数据不足」。例如仅 100 次成功有记录而 900 次终态缺失，不能显示「100% 正常」。

健康颜色建议采用可配置业务阈值。在采集与终态覆盖满足条件后，初始建议：成功率至少 99% 为正常，95% 至 99% 为关注，低于 95% 为异常；样本不足 100 次时标为低样本，不作稳定性结论。这些是待业务校准的默认值，不是行业标准。没有请求显示「无样本」，没有采集显示「未采集」，均不能画成 100% 健康。

### 6.3 分组与模型归属

持久化用户所属分组、请求配置分组、首次实际路由分组、每次尝试的实际路由分组及最终计费分组。`auto` 是路由策略，不作为虚构的采购分组。

经营数据与模型业务调用比例默认按最终归属分组统计：有最终结算时用最终计费组；失败且无结算时用终止尝试组，并标明失败请求。上游执行健康按尝试实际分组统计。跨分组重试的用户最终成功率另按冻结的首次实际路由组形成请求队列，并在指标名中注明，不能用不同队列相减推导重试率。

符合接入条件但找不到渠道的请求也进入整体客户交付成功率。没有实际尝试时不增加渠道健康分母；已能确定服务分组时归该分组的「无渠道」失败，尚未解析服务组时归独立「未解析服务分组」桶。首次实际路由组队列只覆盖实际进入路由的请求，不能作为全站最终成功率的全部分母。

保留客户端请求模型、实际计费模型、上游发送模型和返回模型。模型调用比例默认按客户端请求模型，以表达需求；成本分析可切换计费模型或上游模型。映射关系可在明细追踪。

跨渠道触达请求数不是可相加指标：同一请求经过 A、B 两个渠道，在各自触达数中都出现。总逻辑请求数从请求事实计算；渠道表以尝试数、最终归属请求数分别呈现，不能把触达数求和当总调用量。

## 7 渠道分析功能

### 7.1 全部渠道概览

核心卡片展示逻辑请求数、上游尝试数、净计费额、已知成本、完整集合计费毛利、执行成功率。每张卡片注明时间范围与覆盖情况；性能和重试率在健康区域补充，避免首屏塞入大量同级卡片。

| 区域 | 内容 | 管理价值 |
| --- | --- | --- |
| 经营趋势 | 按日净计费额、估算成本、计费毛利；切换基准额或调用量 | 发现规模与收益变化 |
| 健康趋势 | 按日执行成功率；切换首次成功、超时、TTFT 或耗时 | 发现质量下降与高成本重试 |
| 渠道比较表 | 渠道、当前状态、尝试数、最终归属请求数、净计费额、成本、毛利、毛利率、成功率、P95、成本覆盖 | 比较采购与服务效果 |
| 关注清单 | 负毛利、健康下降、成本缺失、覆盖不足的渠道 | 形成可处理的经营待办 |

首期同屏显示总趋势和选中渠道详情；V1.1 支持选取最多五个渠道进行比较，避免几十条线互相遮挡。比较表支持按毛利、成本、成功率和调用量排序；亏损渠道单独可筛选，不能被高收入渠道的排序掩盖。

健康趋势与经营趋势使用同一时间轴，但分别展示百分比、时间和金额。金额图可显示负毛利。样本数与数据范围显示在 tooltip 中；成功样本延迟和失败超时分开说明，避免排除失败后呈现过于乐观的速度。

### 7.2 单渠道详情

1. 展示渠道名称、类型、标签、成本倍率当前值及历史变更、当前状态和所选期间指标。
2. **每日分组分布**：日 × 分组的堆积柱，可切换最终计费额、基准额、请求数、成本；支持 100% 占比视图。执行尝试分布另作明确切换。负毛利用有正负轴的分组表或分组条形图，避免当作普通占比堆积。
3. **分组贡献表**：分组、调用量、尝试量、净计费额、成本、毛利、毛利率、组内成功率和重试情况。回答该渠道主要服务哪些分组、哪些组合亏损。
4. **模型结构**：客户端与上游模型的调用、tokens 或任务用量、计费额、成本和健康排名，允许按模型钻取。
5. **错误与重试**：超时、限流、凭据、上游余额、网络、协议失败和流式中断分布；已知重试成本与未知成本数量。
6. **关联操作**：打开渠道配置、打开该分组和模型的调度状态、查看对应时间段日志。保留筛选上下文。

分布默认 Top 10 加「其他」，「其他」可展开，所有占比总计为完整筛选集合。请求数和金额分别计算占比，不将高单价模型的金额占比写成调用占比。

## 8 分组分析功能

### 8.1 全部分组概览

| 区域 | 内容 | 管理价值 |
| --- | --- | --- |
| 经营趋势 | 每日最终计费额、成本、毛利、毛利率 | 判断分组定价和采购组合是否健康 |
| 执行健康 | 每日组内成功率、超时率、TTFT 与耗时 | 发现分组服务质量变化 |
| 用户体验 | 首次实际路由组队列的最终成功率、首次成功率、重试恢复 | 识别重试兜底掩盖的问题 |
| 分组比较表 | 分组、最终归属请求数、金额、成本、毛利、成功率、关键模型健康、成本覆盖 | 识别高量低利和低量亏损分组 |

展示分组普通配置倍率及是否存在特殊倍率。跨请求的实际有效倍率应通过基准金额加权后解释；不把不同用户特殊倍率的简单平均当成经营倍率。分组成本由渠道实际成本累计形成，不能平均渠道倍率后乘总收入。

### 8.2 单分组详情

1. **每日经营与健康曲线**：支持点击某日下钻小时，定位异常发生时段。
2. **模型调用比例**：默认按唯一逻辑请求数展示横向比例条与排行，支持切换成功调用、计费额、成本；任务按任务计数，补扣不新增调用。
3. **每日模型组合变化**：日 × 模型的堆积柱，识别昂贵模型占比上升或热门模型健康下降。
4. **渠道贡献**：渠道列表展示承接量、尝试量、计费额、成本、毛利、组内成功率、P95 和备用能力。
5. **模型与渠道矩阵**：V1.1 提供，查看组内一个模型由哪些渠道承接，以及各自健康、成本和流量份额。
6. **亏损定位**：首期提供负毛利模型与渠道排行；V1.1 按模型、渠道、特殊倍率和重试费用进一步分解，显示导致负毛利的组合。
7. **用户与 API Token 分布**：作为二期补充，定位流量集中来源；不在首期复制通用用户分析页面。

分组页的经营趋势与执行健康并排，指标明确注明分组归属。用户最终成功率队列另列，跨组恢复明示来源和目标，避免同名分组显示不同口径却无法理解。

### 8.3 供应依赖分析

二期展示最大渠道流量占比、Top 3 渠道占比、关键模型的有效备选渠道数，以及可观测的供应异常时段。备选是否有效需要配置和近期健康证据，不把「配置了两个渠道」直接解释为具备可靠冗余。

没有调用或主动探测时，系统无法证明该时段可用，不生成全天 SLA 或故障分钟数。若后续需要可用时长指标，应单独建设探测和状态事件采集，并与生产请求分开。

## 9 筛选 对比 钻取与导出

时间默认最近七个自然日，含今天；今天标「未完成日」。支持今天、昨天、最近七天、最近三十天及自定义。默认按日，单日下钻小时；更细分钟诊断由调度中心或二期历史能力承接。

首期固定站点经营时区，建议初始为 Asia/Shanghai，并在页面与导出显示。UTC 保存原始时间，按经营时区归桶；时区变更必须重建聚合或版本化，不允许直接重贴日期标签。查询内部采用左闭右开时间区间，处理边界与跨日，复用日志路由时适配其时间戳单位及区间契约。

渠道、分组、模型、采购供应商和上游 Key 提供有界选择，首期可交互的组合严格按第 20 节白名单。更多筛选逐步提供 Key 业务标签、渠道标签、协议提供商类型、业务模式、资金来源、计费模式、成本完整状态及主动测试。每项筛选必须有对应投影和一致口径后才启用；未支持项显示暂不支持或后台分析，不能默认承诺任意组合。采购供应商与模型品牌、协议类型分别标明。主动测试独立展示，不混入用户需求和计费收入。

环比使用等长期间。今天与昨日相同已过时段对比，不能将今日半天与昨日全天比较。成功率变化用百分点，金额与次数用百分比；基期为零或缺失时显示「无可比基期」。

钻取顺序为总览 → 渠道或分组 → 日期 → 模型或交叉组合 → 请求与账务明细。图表点击与表格筛选联动，同时提供清除筛选入口。恢复上一级时保留排序和选择。

首期提供当前聚合表 CSV 导出，包含时间、时区、筛选条件、指标口径、覆盖率和成本来源。原始账务明细导出单独受权限与数量限制；大范围导出改用异步任务并显示进度。图表图片、日报和外部通知放后续阶段。

## 10 数据质量与特殊状态

| 状态或边界 | 页面与计算规则 |
| --- | --- |
| 无调用 | 调用量可为零，成功率与延迟为无样本，不画为健康或故障 |
| 未开启采集或历史未覆盖 | 对应段落显示未采集，保留曲线断点和采集起始时间 |
| 采集延迟 | 显示最后完整时间与当前暂定数据，允许重试刷新 |
| 成本缺失或规则不足 | 金额为未知；显示缺失规模和配置入口，排除完整毛利计算 |
| 部分成本可知 | 展示已知成本及未覆盖数量，不把它当完整总成本 |
| 使用本地估算用量 | 显示估算来源，与上游实测及供应商对账分层 |
| 求值失败而保留预扣 | 标记结算异常，实际基准额未知，不伪造最终值 |
| 用户取消或流式中断 | 业务结果、已产生用量与已知成本分别保存，健康按责任分类 |
| 调用处理中或任务待结算 | 显示待完成、待结算，不进入已结束成功率和确认毛利 |
| 退款晚于调用 | 按事件发生时间冲减，并关联原请求；用户退款与上游退款独立 |
| 渠道停用或删除 | 当前状态与历史健康分开，历史身份和金额仍可追踪 |
| 请求量低 | 数值和样本数可见，稳定性标签为低样本 |
| 毛利率分母非正 | 显示无适用计费基数，同时展示负毛利绝对额 |
| 未知失败终态 | 独立未知计数，不能补成成功；事件对账修复后更新 |
| 终态覆盖不足或未核验 | 即使已知样本成功率高，也不给健康正常结论，显示数据不足 |

页面显式区分：使用上游报告用量按倍率计算的成本、使用估算用量按倍率计算的成本、供应商对账成本。即使上游用量真实，倍率成本仍然是采购估算。

采集覆盖率必须来自可核验的接入计数、事件投递与对账机制。无法独立核验时显示「覆盖率未核验」，不能因为成功写入的记录看起来齐全而宣称 100%。

## 11 数据建设与实现交接

### 11.1 建议的数据契约

下列为新增设计，具体表拆分在技术设计时确定，不能直接把现有日志 JSON 作为全部事实来源。

| 对象 | 最少内容 |
| --- | --- |
| 渠道成本规则 | channel_id、nullable cost_ratio、version、生效时间、变更审计 |
| 采购供应商与账户 | supplier_id、account_id、ownership_version_id、名称、采购主体、核算币种、共享配额归属、状态与版本 |
| 上游凭据与绑定 | upstream_credential_id、credential_version_id、别名、supplier_id、account_id、状态、标签关联、渠道绑定 ID；分析对象不保存秘密副本 |
| 请求事实 | request_id、task_id、开始与结束时间、请求终态、首次路由组、最终归属组、模型维度、流式标记、业务类型、资金来源 |
| 任务生命周期事实 | 与请求关联的 task_id、提交尝试及凭据和 ownership_version_id 快照、提交接受结果、终态、排队与执行时间、完成时间、结算状态；任务终态幂等记录一次 |
| 尝试事实 | attempt_id、request_id、渠道与名称快照、upstream_credential_id、credential_version_id、supplier_id、account_id、ownership_version_id、绑定 ID、实际路由组、计费与上游模型、开始与结束、客户和供应商结果及责任、上游请求 ID、毫秒延迟、成本规则与计价版本快照、用量来源、模型和工具成本基值 B_i |
| 最终计费快照 | 实际用量来源、模型与工具基值、合计基值、有效分组倍率、定价版本、实际结算额、额度换算尺度、结算状态 |
| 账务与成本事件 | 唯一 event_id、关联请求与尝试、冻结的采购归属与 ownership_version_id、事件种类、金额方向、发生时间、来源与可靠性、原事件关联 |
| 小时与每日聚合 | 站点、渠道、分组、供应商、Key 的固定对象投影与少数交叉投影；计数、金额、质量标记和可合并延迟分布，不展开所有维度组合 |

经营成本按各尝试所属渠道归属，收入只归最终服务渠道。请求相关成本在经营分组上归最终计费组，尝试执行分析保留其实际路由组。最终失败但有成本且没有计费组时，归终止路由组并标明归属来源。这样渠道汇总与经营分组汇总在同一集合上可以核对，同时不丢失跨组重试诊断。

请求与模型比例从请求事实计算；渠道执行健康从尝试事实计算；金额从账务事件与成本快照计算。对于跨渠道去重指标与比例，分别提供可加和指标和去重总数，避免前端自行相加。

### 11.2 可靠性与聚合

在既有实际结算边界采集事实，沿用当前计费引擎完成金额计算，不另造一套通过 token 总量乘平均单价的公式。使用可靠持久化与可重放投递，幂等处理事件；多节点归并不依赖某一进程的内存。

主库与日志库可能分离，不能假定能用一个数据库事务同时提交。技术设计须说明事实持久化、投递、失败重试和对账修复的边界。统计查询以增量小时与每日聚合为主，明细用于钻取和核验，避免每次扫全量日志。

比率由分子、分母汇总后计算，不平均各渠道成功率或毛利率。P95 使用可合并直方图或其他经过验证的分布摘要，不平均小时 P95 或用平均耗时推算分位数。不同流式、模型和任务类型的性能保持可区分。第 20 节进一步规定查询投影、缓存水位、写入幂等和后台资源预算。

建议采集后两分钟内反映到今日暂定数据；历史日桶支持迟到事件修正并显示最后修订时间。具体保留期需结合调用量确定，初始容量方案可按明细九十天、每日聚合十三个月估算；延迟退款与账务关联需独立保留，不能随普通调用日志清理而失去核算依据。

### 11.3 历史数据

消费历史在来源与完整性可说明的前提下回填既有金额和分布。没有历史成本倍率、实际基值或可靠终态时，成本和健康标记未采集，不用当前配置回算成真实历史。

如果管理员需要历史估算，二期提供独立重算任务：指定规则、生效区间和估算来源，保留原始事实，生成估算版本。真实采集、历史估算与对账修订不得混为同一无标识曲线。

## 12 权限与信息可见性

能力分为分析读取、成本查看、成本编辑及导出。首期可由管理员默认拥有，后续映射到现有授权体系；后端每个接口独立校验权限，侧栏隐藏只是展示规则。

成本倍率、采购成本和毛利不出现在普通用户的接口或日志公共字段中。无成本权限时，聚合结果、图表 tooltip 和导出都移除相关数据。API 返回成本信息的范围不因管理员页面路由可见而自动扩大。

成本变更与导出留审计记录，保留操作者、对象、变更内容、时间和结果。分析事实不新增提示词正文、完整请求头、密钥或其他无关敏感内容。

上游 Key 分析只使用别名和不含秘密的永久 ID，接口、缓存、日志、导出与错误消息都不带可用凭据；业务标签不得填入真实 Key。元数据编辑权限与秘密读取、替换、启禁权限分开，查看分析不获得秘密披露能力。涉及凭据秘密或状态的敏感操作沿用既有服务端权限与重新验证机制，并验证 CSRF、过期、重放与旁路；元数据编辑记录非秘密变更审计。[OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)、[Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)、[Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

实施安全验证以 [OWASP ASVS 5.0.0](https://owasp.org/projects/asvs) 为当前参考基线；技术设计识别实际修改机制对应的要求 ID，回归验证后记录结果。本规划不宣称已完成安全合规验证。

## 14 核心验收场景

| 场景 | 可验证结果 |
| --- | --- |
| B=100、G=1.2、K=0.7 | 计费额 120、估算成本 70、毛利 50、毛利率 41.67% |
| 特殊用户分组倍率覆盖普通倍率 | 使用本次实际生效倍率，金额与用户结算一致 |
| 调用后把成本倍率由 0.7 改为 0.9 | 历史成本仍为 70，新尝试按 0.9，进行中与任务沿原快照 |
| 成本倍率为空 | 显示未知和覆盖缺口，不显示零成本或虚假毛利 |
| 成本倍率显式为零 | 已确认免费成本为零，与未配置状态区别 |
| 分组倍率零、基值非零 | 用户计费为零，采购成本保留，显示负毛利 |
| 模型售价零但供应商收费 | 标记成本规则不足，不能当免费采购 |
| A 失败、B 成功 | 一个逻辑请求、两个尝试；A 失败不被最终成功覆盖，收入只确认一次 |
| 重试失败尝试成本未知 | 完整毛利未知，显示已知成本与未覆盖尝试 |
| 自动分组跨组重试 | 经营按最终计费组，执行按各尝试组，首次路由队列另有稳定归属 |
| 同一请求经两个渠道 | 总逻辑请求数为一，不把渠道触达数相加成二 |
| 流式 HTTP 200 后中断 | 执行和业务结果反映中断，不因返回 200 自动成功 |
| 错误日志关闭或消费日志被清理 | 独立采集仍可统计；不能采集时明确显示缺口 |
| 任务提交、完成补扣、再退款 | 模型调用量不增加；最终计费及调整方向正确，预扣不重复确认收入 |
| 任务提交成功但最终失败 | 提交接受率与任务终态成功率分开，业务成功不被提交状态掩盖 |
| 任务失败释放预扣 | 待结算金额清除，未确认收入不生成负收入；仍保留实际采购成本 |
| 任务本地超时但上游终态未知 | 客户失败、供应商结果未知、成本待确认分别保留 |
| 有效业务请求未找到渠道 | 整体交付成功率计入失败，不凭空增加渠道尝试数 |
| 整请求预算耗尽或网关本地错误 | 客户交付失败和网关责任可见，不自动归责某个供应商 |
| 已知样本全部成功但多数终态缺失 | 展示可判定成功率与低覆盖，不显示健康正常 |
| 用户退款而上游不退 | 收入下降，成本不下降，毛利正确减少 |
| 订阅请求钱包扣款为零 | 订阅计量与钱包实扣分开，不标成现金收入 |
| 缓存、图片、音频、工具或任务用量 | 复用真实结算基值，不漏工具费用，不重复计费量 |
| 数据跨午夜、时区或查询边界 | 事件只落一个正确桶，今日比较使用相同已过时段 |
| 多节点重复投递或进程重启 | 事件幂等、不重复累计，已持久化事实不丢失 |
| 汇总分位数与比率 | 从分布与计数汇总，不平均 P95、成功率或毛利率 |
| 渠道删除或分组变更 | 历史数据保持归属与快照，可持续钻取 |
| 普通用户请求相关接口或导出 | 无法获取成本倍率、采购成本和毛利 |
| 图表筛选和 CSV 导出 | 同一范围金额与计数一致，Top N 的其他项不丢失 |

金额核对使用最小确定性样本和代表性历史数据；统计与账务逐请求可追踪。不同层不机械重复同一测试，集中保护结算、事件归属和统计契约。

## 17 上游 API Key 管理与消耗分析

### 17.1 采购身份与标签

```text
采购供应商 supplier_id
  采购账户 upstream_account_id
    上游凭据 upstream_credential_id
      凭据版本 credential_version_id
        渠道绑定 channel_credential_binding_id
```

供应商代表实际采购或结算交易方，例如直连厂商、代理商或转售商；账户代表共同的账单、余额、资源包或合同。模型品牌和渠道协议类型不能替代采购主体。渠道与凭据之间可以多对多：一把 Key 可供多个渠道使用，一个多 Key 渠道也可能使用不同采购归属的凭据。

Key 登记界面提供别名、供应商单选、采购账户、业务标签多选、成本倍率覆盖和关联渠道。供应商在界面中可显示为「上游标签」，但实际保存稳定 supplier_id。业务标签如正式采购、备用、活动资源、测试和合同批次，保存为独立多值关联。

| 对象或变更 | 身份与历史规则 |
| --- | --- |
| 单 Key 渠道 | 同样登记永久凭据 ID，不只处理多 Key |
| Key 改名、排序、启停或移动渠道 | 永久凭据身份不变，绑定与状态独立变化 |
| 同一采购凭据跨渠道使用 | 引用同一个凭据对象，各尝试按实际渠道分布；不能因多个绑定重复计算成本 |
| 正式轮换 | 同一逻辑凭据新增版本，保留旧版本历史与在途任务归属 |
| 列表位置替换为无关 Key | 新建凭据身份，不能继承原位置历史 |
| 更换采购供应商或账户 | 后续尝试采用新 ownership_version_id，历史保留发生时快照 |
| Key 或绑定删除 | 历史对象归档，报告仍可追踪永久身份 |
| 未登记供应商 | 进入未归属采购桶，保留金额与缺口，不从协议名称推断 |

登记和迁移时可通过服务器内部、带账户与认证上下文的 HMAC 指纹辅助检测重复。公开身份使用独立合成 ID，指纹不返回浏览器或导出。不同认证机制、地址与账户的相同字符串不自动合并；组合凭据的识别遵循适配器语义。

业务标签默认用于筛选当前凭据集合；一个 Key 同时有多个标签时，各标签统计相互重叠，不能相加成总成本。供应商排行始终按唯一采购归属统计。若需要按历史标签重新分类，使用明确的标签版本和后台重算，不在打开页面时对明细执行多对多标签连接。

别名和标签编辑可扩展已有多 Key 管理 Dialog，管理入口与分析详情共享同一份元数据。凭据全局状态与渠道绑定状态分别显示；某个绑定被禁用，不等于该 Key 在所有渠道均不可用。分析页面只显示别名、合成 ID 和版本，不依赖真实 Key 前缀识别。

### 17.2 Key 分析首屏与详情

首屏优先展示花费及风险：所选期间已知采购成本、归属净计费额、完整集合归属毛利、活跃 Key 数、未归属与成本缺失规模。默认按成本降序，提供负毛利、认证失败、限流升高、成本未配置和异常增长快捷筛选。

| 页面区域 | 指标或内容 |
| --- | --- |
| 当前页 Key 排行 | 别名、供应商、标签、绑定渠道数、尝试数、最终归属请求数、计费额、成本、毛利、成功率、最近调用、状态、覆盖率 |
| 每日趋势 | 成本、归属计费额、归属毛利、有效尝试成功率；可切换调用量和用量 |
| 渠道分布 | 同一 Key 在各渠道的使用、成本与健康，识别重复绑定和流量集中 |
| 模型分布 | 客户模型及上游模型的调用、计费用量、成本、毛利与错误 |
| 分组分布 | 经营按最终计费组，健康按尝试路由组；按支持范围加载，长范围组合后台分析 |
| 失败与重试 | 上游认证失败、限流、超时、已知失败费用、恢复结果和未知成本 |
| 版本与规则 | 凭据版本、采购归属变更、成本覆盖与继承来源、生效时间 |
| 关联操作 | 打开渠道多 Key 管理、编辑元数据与成本、查看关联请求链路 |

同一 Key 跨渠道的逻辑触达数不可通过渠道行相加得到；默认显示可加和的尝试数与唯一最终归属业务请求数。需要触达去重指标时在后台投影阶段维护，不让榜单实时执行全量 COUNT DISTINCT。

余额、可用额度、到期时间与资源包剩余量仅在有供应商来源时展示，附更新时间和数据范围。共享账户余额只计一次，不把每个 Key 显示的同一余额相加；同一账户下的限流也可能共享，不能将十把 Key 理解为十倍供应容量。

### 17.3 Key 成本与利润归属

每个尝试记录 B_i、有效 K_i、实际成本或估算成本及来源，首期 K_i 按「Key 覆盖 → 渠道默认」解析。收入归最终服务 Key，成本归每次实际使用的 Key。若 Key A 失败后 Key B 成功，A 保留失败成本，B 获得请求收入，二者的归属毛利可以在同一完整请求集合中核对到总毛利。

归属毛利描述账务如何分配，不足以单独证明某把 Key 更划算。详情另提供「最终服务请求全链路毛利」，扣除这些请求在其他 Key 和供应商上的重试成本。两个指标分别标注，不能在同一个总计中混加。

同一 Key 在多个渠道继承不同成本倍率，或各渠道采用不同平台基价时，显示规则差异及近似范围。后续独立采购价格解决不成比例的计价结构，不能用一个平均倍率掩盖差异。

### 17.4 异步任务与历史兼容

任务提交时保存提交尝试、凭据 ID 与版本、供应商、账户和成本规则快照。生成成本始终关联真正提交任务的凭据；轮询改用另一把 Key、Key 排序、渠道配置变化不能转移历史生成成本。轮询认证失败单列为查询链路问题；若供应商确实对查询收费，记录独立查询费用，不能重复记生成调用。

当前 [任务初始化](/Users/bobdong/项目/智能路由-v2/model/task.go:241) 仅在部分渠道保存提交秘密，没有统一采购身份。新设计增加非秘密的身份快照，具体秘密生命周期继续由既有凭据机制管理，分析系统不复制秘密。

迁移时为当前绑定建立稳定身份和生效时点。缺乏可证明绑定版本的历史 multi_key_index 进入「历史 Key 不可归属」，不能按当前列表序号分摊旧消耗。可证明的旧单 Key 归属也需验证期间是否替换过秘密或供应商，不能默认整段历史恒定。

## 18 上游供应商统一经营分析

### 18.1 供应商首屏

将同一采购主体下全部账户、Key 和渠道的实际尝试统一归并。首屏显示总采购规模、归属计费额、完整集合归属毛利、供应质量、成本集中度及未归属费用。

| 指标组 | 内容 | 管理员判断 |
| --- | --- | --- |
| 经营 | 每日净计费额、成本、毛利、毛利率与覆盖 | 哪个采购上游值得增加预算，哪个正在亏损 |
| 质量 | 执行成功率、限流、超时、流式完整率、分模式 P95 | 低采购单价是否被失败和重试抵消 |
| 构成 | Key、渠道、分组与模型的费用和调用份额 | 成本上涨来自哪种业务或凭据 |
| 依赖 | 采购 Top 1 / Top 3 占比、关键模型的供应来源 | 是否存在共同供应商或共享账户的集中风险 |
| 采购账户 | 账户消耗、共享余额与限额、更新时间 | 是否需要充值、换采购方案或增加独立备份 |
| 可信度 | 未归属、成本未知、用量估算、账单未对账 | 当前毛利结论可用范围有多大 |

供应商排行默认按成本排序，可切换毛利、毛利率、健康和风险。进入供应商详情后查询其每日趋势与当前页 Key/渠道贡献，再按需展开模型与分组拆分。

供应商横向比较应同时固定模型、计价单位、业务模式与样本范围。每千次成功业务的全链路成本可以作为补充效率指标，但不同模型结构不一致时不能据此直接得出采购优劣。

### 18.2 统一归属与可加和性

收入只归最终服务供应商，成本按各实际尝试供应商发生。跨供应商重试时，一个逻辑请求可能触达多个供应商，但只确认一次收入。供应商 Key 数来自永久身份去重，不将各渠道 Key 数相加。

四个 Tab 使用同一账务与完整请求集合，金额可沿渠道、Key、供应商和经营分组分别核对。经营的已知成本总计可以保留失败但没有收入的供应商费用；完整毛利总计仍遵守全请求成本完整规则。

供应商改名只改变展示名称；采购主体变更保留事件快照。默认报告使用发生时归属，若要按当前组织重新分类，生成单独标记的报告版本。供应商未知或历史 Key 不可归属的费用单列，不能从总成本消失。

归属版本与凭据秘密版本分别维护。收入沿最终服务尝试的采购归属确认，任务跨日完成仍沿提交快照；退款沿原账务事件的供应商和账户归属。不能使用当前 Key 表连接补历史采购归属。

### 18.3 账单与余额能力

供应商用量或账单采集由独立后台任务按账户限速、缓存和重试，页面只读取最近采集结果。打开页面不逐 Key 发起余额或账单请求。接口失败显示更新时间与失败状态，不删除最近有效值。

充值属于采购现金支出，余额下降也可能包含资源包、调账或多个应用的使用，两者都不能直接等同本系统调用成本。实际费用对账需保留供应商账单行、时间、账户、币种、用量与可关联上游请求 ID，匹配本系统事实；无法逐请求匹配时显示账户级对账与分摊假设。

预测剩余可用天数仅在余额单位与成本口径可比、有足够完整历史且不存在无法解释的共享消耗时计算，并标「按近期消耗估算」。首期无真实数据来源的指标展示未支持；对账和预测在后续阶段实现。

## 20 数据库性能与查询治理

### 20.1 数据链路

```text
缓存中的采购身份和规则 → 请求/尝试/结算事实
  → 持久化事件与投递确认 → 有限并发的小批量聚合
  → 对象小时/每日投影与常用交叉投影
  → 带水位的查询缓存 → 当前 Tab 的批量接口
```

请求热路径从已有渠道配置缓存取得采购身份、绑定和规则，一次带入事实。Key 注册、去重指纹及标签解析在配置阶段完成，不能每次请求扫描所有 Key、计算全库指纹或增加供应商、账户、标签多表查询。

主库仍支持 SQLite、MySQL 与 PostgreSQL。可靠事件身份、确认状态和首期核心聚合不依赖 ClickHouse；大规模部署可将分析副本发送到独立分析存储，但具体兼容和数据一致性另行验证。现有日志库可以分离，不能假定跨库事务。

### 20.2 控制写入开销与保证幂等

在实际结算边界持久化事实或可靠投递意图。能与账务同事务提交时采用同事务；不能时明确失败补偿和核对机制。内存队列只能缓冲，不能作为唯一经营事实。

后台以有界小批次写入，初始建议每批 100 至 300 事件、每 1 至 5 秒或达到阈值提交，按实际数据库参数上限、事件宽度和锁等待校准。短暂交换内存缓冲后释放锁，再执行数据库工作，不能持有全局统计锁逐行访问数据库。

同一事务内提交新事件收据、贡献差量和消费进度；event_id 与事实版本重复时不产生第二次贡献。提交结果不确定时安全重放。开始、结束与终态修订更新同一事实的贡献，不算三次调用。不能直接向现有累加 upsert 重投不确定批次。

幂等收据、事实最后贡献与紧凑账务归属状态有独立保留策略，至少覆盖允许的重放、迟到及财务修订窗口；普通九十天明细清理不能同时删除这些依据。归档采用已封存进度、事实版本和明确接收截止窗口，超窗口旧投递拒绝直接累加，走受控核对修正。未结任务、未确认成本和允许退款的账务关联不清理；如果要求十三个月聚合都可重放，保留相应幂等依据并计入容量预算，不能只留汇总数字。

SQLite 使用有限的单分析写者和短事务；MySQL/PostgreSQL 允许少量固定分片并发，聚合行按固定顺序更新，控制争用。消费者租约与 CAS 按三库能力实现，不要求 SKIP LOCKED。跨天退款、迟到终态和未知成本转已知时，只修正有关请求与桶，不扫描重算全部历史。

请求事实保存成本完整状态和版本。补齐一项成本后，后台维护该请求在渠道、Key、供应商和经营分组上的完整集合贡献；查询时直接读投影，不临时连接全部 attempts 判断是否完整。保存可重放依据以供修复。

### 20.3 少数预聚合与查询支持范围

| 投影 | 保留的主要粒度 | 服务的页面 |
| --- | --- | --- |
| 对象每日汇总 | 站点、渠道、分组、Key、供应商及采购账户各自的日桶；计数、金额、质量与分布摘要 | 摘要、每日趋势、排行与账户详情 |
| 对象小时汇总 | 已观察到的对象小时桶，保留较短时间 | 单日下钻及选中对象短期趋势 |
| 渠道分组模型拆分 | 实际发生的渠道 × 分组 × 模型 × 日；经营与执行分别归属 | 原渠道分组分布、分组模型比例 |
| Key 渠道/模型拆分 | 实际发生的 Key × 渠道 × 日、Key × 模型 × 日，按冻结的供应商、账户及归属版本分桶 | Key 基本分布、供应商渠道与模型结构 |
| 固定错误类别 | 有界类别与对象的计数，不使用任意错误文本 | 异常排行与错误分布 |

上述为投影族，物理表可合并或拆分。同一 Key 同日可能更换采购供应商或账户，supplier_id/account_id 并非 Key 加日期的单值属性：所有按采购归属筛选的 Key 投影将事件冻结的 supplier_id、account_id 和 ownership_version_id 纳入桶唯一身份，或采用等价归属分段，再按页面需要合并。同一天 A/X 与 B/Y 分别保留，不能被当前元数据覆盖。只创建实际出现的稀疏归属组合，不展开所有供应商与 Key 的笛卡尔组合；所有新投影评估每事件写放大和实际行数。

不建立供应商 × 账户 × Key × 渠道 × 分组 × 模型 × 用户 × 用户 Token × 节点 × 标签的全维立方体。Key×分组等新增组合先限定选中对象与短时间，按需要增设窄投影；没有合适投影的长范围复杂查询转后台，不能静默回退全量日志扫描。

| 分析操作 | 首期交互支持 | 超出范围时 |
| --- | --- | --- |
| 一个对象类型的摘要、趋势、榜单 | 对象每日/小时汇总直接查询 | 更长范围采用已有周/月投影或后台 |
| 单 Key 的渠道或模型分布 | 窄拆分投影，Top N 和分页 | 多维交叉通过后台报告 |
| 渠道分组与分组模型分布 | 原常用三维拆分，受时间及扫描预算约束 | 长范围或高基数查询后台执行 |
| 供应商 Key/渠道/模型贡献 | 对发生时 supplier_id 过滤窄投影，保留未归属 | 复杂混合过滤需对应投影或异步 |
| 多值标签筛选 | 元数据索引解析为去重 ID 集合或半连接；不展开金额多份 | 大集合后台执行，不拼超长 IN |
| 标签 × 历史归属 × 多维交叉 | 明确版本的后台报告 | 不作为首屏自动查询 |
| 原始请求与尝试 | 指定对象、短时间或精确 request_id 的索引查询 | 全量检索与导出异步 |

同一分析查询的所有区域必须使用一致的过滤语义。选择某 Key 后，若某个摘要投影不支持该组合，明确限制或切换查询计划，不能显示全站摘要配筛选后的榜单。

首期查询白名单如下；每项还服从对象数量、时间、扫描和点数预算。客户端隐藏不支持项，服务端同样验证组合并返回明确错误或后台任务入口。

| 页面 | 首期可交互组合 | 首期不默认同步支持 |
| --- | --- | --- |
| 全部对象总览 | 时间、当前对象类型、自身对象 ID；已投影的业务模式/资金来源 | 任意多个异类维度同时交叉 |
| 渠道与分组 | 选中渠道或分组；渠道 × 分组 × 模型常用拆分 | 再叠加 Key、供应商、历史标签的完整组合 |
| 上游 Key | 选中 Key、当前业务标签筛出的有界 Key 集合、冻结供应商/账户归属 | Key × 分组 × 模型等未建投影组合 |
| 单 Key 基本拆分 | 选中 Key 后按渠道或模型分别拆分 | 渠道与模型再同时交叉的任意组合 |
| 上游供应商 | 供应商/账户；Key、渠道、模型分别贡献 | 供应商 × 分组、历史标签及其他多维同时交叉 |

同步、流式、异步任务与钱包、订阅只在已为相应投影保存固定子计数和金额时启用筛选；计费模式、测试来源及成本状态同理。技术设计选择有限字段或有限分类，不引入用户/Token/多值标签的无限扩维。某个组合所需健康或毛利字段尚未投影时，不能仅筛部分区域，整个组合转后台或明确禁止。实施验收逐项核对功能清单与投影字段，不能只完成 UI 选择器。

### 20.4 API 与数据库预算

以下为实施期初始上限与性能目标，须在实际规模和硬件上验证，不能作为已测得结果。

| 操作 | 初始约束 |
| --- | --- |
| 当前 Tab 首屏 | 一个批量接口返回摘要、双趋势、当前页榜单和质量；冷缓存业务数据 SQL 总数不超过 6 条，含一次批量名称补全 |
| 对象比较 | 一次请求最多五个对象，禁止逐对象独立查询 |
| 排行与元数据 | 默认 50 行、上限 100；服务器筛选排序，不附每行全历史 |
| 单对象详情 | 一个接口取摘要、趋势与一个默认拆分；错误、分组和明细展开后再加载 |
| 日粒度交互 | 默认七天，首期上限九十天；更长读长周期投影或异步 |
| 小时趋势 | 默认单日，上限三十一天，最多约 744 点；展示时区的特殊边界单独验证 |
| 图表与拆分 | 默认 Top 10 加其他、比较最多五条系列，限制总点数与响应大小 |
| 多选 | 每类初始最多五十个对象；站点或供应商全量通过范围条件处理，不列出全部 Key |
| 原始明细 | 默认 24 小时，上限七天，要求 Key/渠道/供应商约束；精确 request_id 可单独追踪 |
| 明细分页 | 默认 50、上限 100，稳定时间加 ID 游标，limit+1 判断 has_more；默认不求全量精确 COUNT |
| 分析读执行 | 初始数据库查询总预算两秒，设置驱动可验证的取消与超时；超预算返回可解释状态或建议后台分析 |

首屏数据 SQL 预算不含既有认证校验，但仍监测整个请求资源使用。单个 API 合并请求不代表可以内部生成数百条 SQL，记录实际 SQL 次数、扫描量和耗时。

聚合排行允许在有界对象集合与期间上汇总排序；超大对象量或昂贵 P95 排序使用已发布的排名快照或后台任务，不能将所有 Key 的完整直方图拉到应用中再排序。关键聚合字段与常用条件结构化，禁止扫描日志 other JSON、秘密数组或任务 PrivateData。

索引围绕真实访问路径选择，例如对象 ID + 桶时间，以及明细 credential_id/channel_id/supplier_id + 时间 + 事件 ID；唯一键保证投影与事件身份。每个候选索引通过三种数据库的执行计划和写入成本验证，不为所有筛选组合建索引。大范围总数、深 OFFSET、无界模糊检索不属于默认交互能力。

### 20.5 缓存 水位与前端加载

查询缓存键包含权限范围、规范化筛选、经营时区、口径版本、投影水位、粒度和分页排序。无成本权限不能命中含采购信息的未裁剪缓存。

今日暂定数据初始缓存 30 至 60 秒，完整历史缓存 5 至 15 分钟；退款、迟到或归属修订后按投影版本失效。合并同键并发请求，限制条目数量，短暂缓存空结果。缓存故障时只允许有界回源或最近已知快照，不让回源风暴耗尽主库连接。

首期统一读取已持久化聚合并显示完整水位。未落库数据暂不混入，不能把数据库累计、Redis 累计和各节点热缓存直接相加。后续实时投影必须证明与持久化范围互斥及事件去重。多个投影进度不同，首屏采用共同完整水位与已发布快照版本，避免拿不同时点的收入与成本相减。

发布版本必须约束实际读取，不能只是缓存标签。首屏多条 SQL 使用同一短一致性读取与已发布数据版本，不通过独立连接读取不断变化的最新行；发布点与有关投影的更新保持原子，不能原子发布时提供可读取的版本化贡献或快照。版本水位元信息与数据一起返回，支持从同一版本重现指标。

分块导出固定事实高水位和口径版本，读取可重现的版本或后台物化报告；旧版本在任务结束或超时前保留。迟到修订产生新版本，不改变进行中的报告。SQLite 不使用贯穿整个导出任务的长读事务维持快照。若尚无固定版本或受控物化能力，只允许短事务内取得的有界聚合导出，不宣称超大多块报告具有一致快照。

前端只请求当前 Tab；点击对象后再取详情，折叠区域不预取。筛选通过应用动作或合理防抖触发，取消过期请求，保留旧结果并标更新中。默认每 60 至 120 秒刷新今日分析，历史默认不轮询，后台或隐藏页面暂停；调度中心的实时刷新不直接复制到经营页面。

### 20.6 后台任务与网关资源隔离

长范围分析、历史重算、精确总数、复杂组合和大导出进入后台任务，参考已有 SystemTask 的进度、租约、取消和重试。按小块读取与写出，避免一次加载数十万行到内存。导出保留权限、筛选、口径、水位和失效时间。

分析读取、聚合写入、导出和余额采集分别设置并发预算，预留网关业务连接与 CPU。起始可按每管理员最多两个分析读请求、全实例四个分析读执行、一个导出任务校准；各节点配置必须服从数据库级总预算，不让增加节点后并发无限扩大。

主库负载或积压升高时，先限制导出与复杂分析，返回缓存快照并注明延迟，适度降低后台批次；可靠事件继续保留并监测磁盘/队列容量。不能丢弃账务事实换取页面流畅，也不能无上限堆积直至拖垮业务。实际容量耗尽策略在技术设计中明确告警、暂停可选任务及必要的业务降级边界。

SQLite 重点验收短事务、读写锁等待与单写者预算；MySQL/PostgreSQL 重点验收热点聚合行、死锁重试、连接等待和大排序。读副本或分析库用于大规模部署时显示其延迟，迁移与实时一致性另行核验，不要求首期用户必须新增数据库。

### 20.7 性能验收与容量模型

实施前登记每日业务请求与尝试数、重试分布、活跃 Key/账户/供应商/渠道/模型/分组数、实际组合数、节点数、并发管理员、保留期、硬件和数据库版本。使用确定性合成或获授权脱敏数据验证当前容量与预期增长，禁止复制真实秘密。

事实增长按实际事件数评估，聚合增长按每日不同活跃组合数评估，不能用所有对象数量乘积粗算后盲目建表。记录平均事件字节、索引开销、每事件投影写次数、保留期磁盘需求和查询扫描行数，决定是否增加特定投影或独立分析副本。

| 验收项 | 初始目标或必须记录的结果 |
| --- | --- |
| 首屏延迟 | 热缓存 P95 不超过 300 ms，冷缓存不超过 1.5 s，按目标部署校准 |
| 暂定数据延迟 | 常态两分钟内发布；超出显示积压、水位与原因 |
| SQL 与扫描 | 首屏不超过约定 SQL 数，无逐 Key N+1、无日志 JSON 扫描和无默认明细 COUNT DISTINCT |
| 对业务影响 | 与分析关闭基线比较网关 P95、数据库 CPU/IO 和池等待；初始讨论目标为 P95 恶化不超过 5%，须真实并发验证 |
| 写入正确性 | 重复投递、未知提交、重启与迟到修订不重复累计，不丢已确认账务 |
| 资源上限 | 聚合、导出、余额采集同时运行仍服从数据库总预算，取消与降载有效 |
| 存储增长 | 给出事实/索引/聚合的真实行数与大小、写放大及保留期预测 |

SQLite、MySQL、PostgreSQL 分别记录正确性、迁移及性能结果，不用某一数据库的性能推定其他数据库。SQLite 在大规模目标下若不能达到同一延迟，应明确支持容量和部署选择。以上均为待实施验证的目标，不是本次规划已经完成的压测。

| 余额查询或账单接口不支持 | 显示未支持或过期，不制造实时余额与对账成本 |
| 分析接口、缓存、导出和审计 | 不出现真实 Key、认证头或秘密副本；越权请求被服务端拒绝 |

## 22 同步调用首版实施交接 · 2026-10-08

### 22.1 已实现范围

管理员「渠道」之后新增「渠道概览」，正式路由 `/channel-overview`，提供渠道、分组、上游 Key、上游供应商四个 Tab。当前页面支持 7/30 天和对象下钻，显示请求与尝试数、计费收入、已知成本、完整样本毛利、健康曲线、每日消耗与分布、模型调用分布和排名。后端白名单上限 90 天；前端首版开放 7/30 天。

渠道列表增加可编辑的成本倍率；Key 元数据支持采购供应商、别名、标签及成本覆盖。空值代表继承或未知，零明确代表免费，覆盖规则为 Key → 渠道 → 未知。元数据不返回可用凭据。永久 Key ID 跨渠道复用；列表重排、删除、替换及可信 OAuth 轮换分别保留正确身份、版本和启禁状态，不靠当前列表序号归属历史。

同步转发主入口在实际发送前冻结采购身份、归属和成本版本，在结算时保留同次计算的原价基值与实际确认的资金贡献。覆盖公共 HTTP/SSE、OpenAI Realtime、AWS SDK、Coze、讯飞及火山 TTS 直接发送路径。估算用量、缺失实际图片数量、未覆盖计价路径和歧义单位保持成本或收入未知。消费量与既有用户扣费计算不因分析功能改变。

每次真实重试独立计调用、成本与健康，收入沿实际结算记录；毛利只包含整条请求所有尝试成本已知、资金贡献已确认的集合。筛选掉失败渠道仍不能将不完整请求变成完整利润样本。金额为冻结单位下的额度等值，订阅用量和计费收入不等同实际现金回款。健康采用已结束且可判定尝试的成功率，业务拒绝和客户端取消不作为渠道故障。

历史从启用采集开始，不由旧日志的 Key 序号反推归属，也不根据当前成本规则重算。桶使用 UTC。

### 22.2 已实现的数据库约束

分析事件和日聚合存于主库，独立于消费日志是否启用及其分库配置。持久化待投影事件由后台每秒读取，单批上限 100、单轮最多 10 批、总预算 2 秒；批量状态 CAS 与合并后的稀疏日桶加量同事务提交，失败可重放，重复事件不重复累加。聚合行按固定 ID 顺序更新。

前台只读取聚合，每次请求实测固定 6 条业务 SQL；待采集状态采用有索引的 `EXISTS ... LIMIT 1`，不扫描全部积压数量。查询总预算 2 秒，本机最多 4 个分析读任务，30 秒缓存与同键请求合并；排行/对象列表 100 行，分布最多 900 个每日组合，超出范围显式说明。当前 Tab 一个批量接口，快速切换可取消等待，不自动轮询其他 Tab。

各区域在同一读取快照内执行。SQLite 明确使用 `ReadOnly` 对应的延迟 `BEGIN`，已实测读取期间 WAL 写入可提交，不占 `BEGIN IMMEDIATE` 写者锁。采购镜像在配置更新/数据库读取时解析，缓存中的快照查找为 O(1)，请求不逐 Key 查询供应商；无缓存的轮询元数据查询只选择 `id/channel_info`。

以上属于查询和正确性约束，尚未在真实业务规模上证明吞吐、容量或 P95 目标。事件事实当前保留，不执行自动清理；幂等保留、封存与归档仍需设计后实施，不能直接删除已完成事件来节省空间。采集写失败会产生本机告警和页面提示，但该失败标记目前仅存于节点内存，跨节点/重启后的完整采集证明尚未实现。
