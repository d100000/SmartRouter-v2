# 模型性能与稳定性监控看板需求文档

日期：2026 年 10 月 26 日  
版本：1.1（调研、评审与前端 demo 版）  
状态：需求文档已优化，当前只实现前端示例，不接入真实 API

## 1. 背景与目标

站点当前已经有按模型、分组和小时桶记录的性能数据（`perf_metrics`），也已经在一次 relay 的最终边界采样成功率、延迟、TTFT 和输出 token。现有页面能看到部分模型性能，但管理员无法按「公司 → 模型分组 → 模型」统一比较整站稳定性，也无法在一个页面判断「失败是否被重试恢复、哪家公司正在消耗错误预算、哪一个模型拖累了整体体验」。

本需求建立一个管理员看板，回答四个问题：

1. 过去 24 小时整站和各公司的最终请求成功率是多少？
2. 失败后重试成功是否被正确计为一次成功，重试成本和恢复效果如何？
3. 哪些公司、模型分组和模型的成功率、延迟、TTFT、吞吐或错误类型正在恶化？
4. 管理员如何配置公司及公司下的模型分组，并基于统一口径追踪 SLO 和错误预算？

本期只交付前端 demo 与可评审的产品/数据契约；真实采集、存储、接口、告警和权限在后续实现阶段完成。

## 2. 用户与决策场景

| 用户 | 需要做的决定 | 看板必须提供的证据 |
| --- | --- | --- |
| 站点管理员 | 是否需要切换渠道、调整分组或联系供应商 | 公司/模型稳定性排行、24 小时曲线、错误类型、重试恢复率 |
| 运维人员 | 是否发生局部故障或尾延迟恶化 | 当前小时、最近 3 个小时、P95/P99、数据新鲜度、异常时间点 |
| 数据/经营负责人 | 哪些模型可作为默认路由，哪些模型风险高 | 请求量加权成功率、错误预算消耗、覆盖率和样本量 |

## 3. 关键口径：一次请求、一次尝试与最终结果

### 3.1 三种统计单位

| 单位 | 计数方式 | 用途 |
| --- | --- | --- |
| 逻辑请求（request） | 一次用户可感知的调用只计一次；流式分块、轮询、补扣不新增请求 | 对外体验、最终成功率、最终延迟 |
| 上游尝试（attempt） | 每次实际发送到公司/渠道/模型的调用计一次；失败重试和 fallback 均计入 | 公司/渠道执行健康、错误类型、重试成本 |
| 终态事件（outcome） | 逻辑请求最终成功、最终失败、客户端取消或未知 | 终态覆盖率、数据质量、审计 |

每条逻辑请求必须有稳定 `request_id`，每次尝试必须有 `attempt_id` 和 `attempt_number`。采集器在请求终态只写入一次逻辑请求事实，避免重试回调或多节点重复计数。

### 3.2 24 小时最终请求成功率（主指标）

```text
最终请求成功率 = 最终成功的逻辑请求数 ÷ 已结束且可判定的逻辑请求数 × 100%
```

计数规则：

- 首次失败、第二次尝试成功：逻辑请求只计 1 次，结果计为成功；同时记录 `retry_recovered = true`。
- 首次失败、所有重试均失败：逻辑请求只计 1 次，结果计为失败。
- 尚未结束、状态未知或无法确认上游终态：不进入成功率分母，单独展示终态覆盖率和未知数。
- 客户取消、请求体校验失败、鉴权失败等不代表上游模型稳定性；从模型/公司 SLI 中排除，并在「入口失败」分栏展示。可配置是否纳入整站 API 健康率。
- 结果必须以用户最终收到的有效响应为准；HTTP 200 但流式没有有效内容、协议终态为 error 或 schema 无效，应判定为失败。

这条口径满足“失败后重试成功算成功”，又不会隐藏重试压力。页面同时展示首次尝试成功率、重试请求率、重试恢复率和上游尝试失败率。

### 3.3 延迟与吞吐口径

- **最终响应延迟**：逻辑请求从首次发送到用户收到完整有效结果；包含重试等待，展示 P50/P95/P99。
- **尝试延迟**：单次上游尝试的发送到响应终态；用于定位具体公司/渠道。
- **TTFT**：流式请求从发送到第一个有效 token/内容块；只对存在有效首块的样本计算。
- **输出吞吐**：`output_tokens ÷ generation_time`；成功样本单独计算，不能用请求总耗时替代生成耗时。
- 延迟分位数不能用各小时平均值再求平均，必须由原始分桶/直方图或可合并分位数结构计算；样本不足时显示“样本不足”。

## 4. 看板信息架构

```text
模型性能与稳定性
├── 总览（默认）
│   ├── 时间范围、公司、模型分组、模型、请求类型筛选
│   ├── 6 个核心指标
│   ├── 24 小时稳定性曲线（整站/公司可切换）
│   ├── 公司健康排行
│   ├── 模型成功率排行
│   └── 最近异常与数据质量
├── 公司与模型分组（管理员）
│   ├── 公司列表、状态、SLO、负责人
│   ├── 公司下的模型分组
│   ├── 模型成员与匹配规则
│   └── 保存、停用、审计
└── 详情抽屉
    ├── 请求/尝试/重试漏斗
    ├── 成功率、P50/P95/P99、TTFT、TPS 曲线
    ├── 错误分类与时间线
    └── 下钻到 usage log 的 request_id
```

页面默认 24 小时、1 小时粒度；接口统一用 UTC，页面按界面时区展示并标注时区；当前小时可显示为“进行中”。所有百分比旁边显示样本数，例如 `99.82% · 5,428 requests`，避免小样本造成误判。

## 5. 首屏指标与维度

### 5.1 顶部 KPI

| 指标 | 展示 | 解释 |
| --- | --- | --- |
| 最终请求成功率 | 大百分比 + 请求数 + 环比 | 主 SLI；重试成功按成功计 |
| 首次尝试成功率 | 百分比 + 首次尝试数 | 衡量路由第一选择质量 |
| 重试恢复率 | 百分比 + 恢复数/首次失败数 | 衡量 fallback 是否挽救用户体验 |
| P95 最终响应延迟 | 毫秒/秒 + 样本数 | 用户感知的尾延迟 |
| P95 TTFT | 毫秒 + 流式样本数 | 首字等待体验 |
| 错误预算 | 剩余百分比/消耗速度 | 按可配置 SLO 计算；无 SLO 时显示“未配置” |

### 5.2 公司维度

公司是管理员维护的业务归属，不直接从模型名称猜测。每家公司可有多个模型分组；一个请求保存“请求模型”“实际服务公司/模型”“尝试公司/渠道”的快照，历史数据不随配置改名而改变。

公司排行至少显示：最终请求成功率、上游尝试成功率、请求量、重试请求率、重试恢复率、P95 最终响应延迟、P95 TTFT、主要错误类型、数据覆盖率、最近一次成功时间。

### 5.3 模型维度

提供两个视角并明确标签：

1. **请求模型成功率**：按用户请求的模型聚合逻辑请求最终结果；适合判断用户选择该模型能否成功。
2. **实际服务模型/尝试成功率**：按实际响应模型和每次尝试聚合；适合定位供应商或 fallback 的执行问题。

模型表至少显示：请求数、最终成功率、首次成功率、重试恢复率、P50/P95/P99 最终延迟、P95 TTFT、输出 TPS、错误预算、趋势箭头。请求量低于阈值时不参与“最佳/最差”排序，只显示“样本不足”。

#### 5.3.1 分模型表字段与排列顺序

分模型成功率表提供“字段设置”入口，允许查看者按自己的分析任务编辑显示字段和排列顺序。字段设置只改变当前表格的呈现，不改变成功率、排序口径或底层数据。

默认字段顺序为：

```text
模型 → 公司/模型分组 → 请求量 → 最终请求成功率 → 首次尝试成功率
→ 重试恢复率 → P95 最终响应延迟 → P95 TTFT → 输出 TPS → 状态
```

可选字段至少包括：请求量、最终成功率、首次尝试成功率、重试请求率、重试恢复率、上游尝试成功率、P50/P95/P99 最终响应延迟、P95 TTFT、输出 TPS、429/5xx/timeout 次数、最近异常时间、终态覆盖率、错误预算和状态。字段名称必须说明“最终请求”或“上游尝试”的统计层级，避免把两个成功率混为一列。

交互规则：

- 字段设置面板以复选框控制显示/隐藏，以拖拽调整顺序；同时提供上移、下移和键盘操作，不能只依赖鼠标拖拽。
- “模型”和“最终请求成功率”是必选字段，不能隐藏；模型列固定在第一列，窄屏时允许横向滚动。
- 初次进入使用默认顺序；用户修改后按当前账号、页面和筛选范围保存，刷新页面后恢复。管理员可以另存为该页面的团队默认视图。
- 提供“一键恢复默认字段”和“应用”操作；关闭面板或取消时不保存未应用的修改。
- 修改列配置不应清空筛选、分页、选中模型或当前曲线；字段变化后表头、单元格、空状态和 loading 状态保持对齐。
- 若字段没有数据或终态覆盖不足，显示“未知/样本不足”，不能用 0% 代替；隐藏字段不影响后端查询的口径校验。
- CSV/导出能力上线后默认沿用当前字段与排列顺序，并允许导出时恢复完整字段。

字段配置属于视图偏好，不需要记录业务审计；团队默认视图的创建、修改和删除需要记录管理员、时间和配置版本。接口返回 `available_columns`、`default_columns`、`selected_columns` 和 `column_order`，前端不得根据列名猜测统计含义。

### 5.4 数据经理视角的指标分层

为了避免把不同问题压缩成一个“健康分”，指标按四层呈现：

| 层级 | 主要指标 | 回答的问题 |
| --- | --- | --- |
| 可用性 | 最终成功率、首次成功率、重试请求率、重试恢复率、终态覆盖率 | 用户是否拿到有效结果，网关是否依赖重试才能成功 |
| 性能 | 请求量/RPS、P50/P95/P99、TTFT、生成阶段耗时、输出 TPS、并发/排队时间 | 用户等多久，慢请求是否集中在尾部，系统是否接近饱和 |
| 诊断 | timeout、429、5xx、连接失败、协议错误、内容为空、熔断/cooldown、fallback 成功/失败 | 失败来自哪里，是否可通过路由或供应商动作修复 |
| 经营与数据质量 | 输入/输出 token、单位成本、缓存命中、覆盖率、延迟采集、未知终态、无归属请求 | 成本是否异常，数据是否足以支撑决策 |

“健康分”只作为排序辅助，不替代原始指标；质量评测（正确性、相关性、拒答率、安全性）另建质量看板，不能与线上可用性成功率相加。

## 6. 24 小时曲线设计

- X 轴为连续 24 个小时桶，Y 轴为请求数加权的最终成功率；不对小时百分比做简单平均。
- 支持整站、单公司、公司组和单模型切换；图例显示请求数，悬浮提示同时给出成功数、失败数、重试恢复数、P95 延迟。
- 成功率线与 P95 延迟可叠加为双轴，但默认分成两个可切换系列，避免百分比和毫秒混读。
- 没有请求的小时显示空值/断点；不显示 0% 作为“没有数据”。
- 当前小时使用虚线或半透明背景标记；数据延迟超过 5 分钟时显示数据新鲜度。
- 异常小时可点击打开错误分布和请求列表，保留筛选条件。

## 7. 公司与模型分组配置

### 7.1 公司

字段：`company_id`、名称、简称、状态、默认 SLO、负责人、备注、创建/更新时间。名称变更不覆盖历史快照；停用公司不删除历史数据，也不再接收新模型映射。

### 7.2 模型分组

字段：`group_id`、`company_id`、分组名称、模型成员、匹配方式、成功率 SLO、P95 延迟阈值、最小样本数、启用状态。首期优先使用明确的模型成员选择；通配符/正则匹配作为后续能力，避免规则重叠导致归属不确定。

归属优先级：精确模型成员 > 明确别名 > 未归属。一个模型在同一时间只能有一个生效归属；冲突保存时阻止提交并指出冲突项。未归属模型进入“未分组”行，不丢失数据。

### 7.3 权限与审计

只有管理员可创建、修改、停用公司和分组；普通用户不显示管理入口。配置变更记录操作者、前后值、时间、原因和影响范围。配置页展示“当前配置只影响后续请求，历史指标使用采集时快照”。

## 8. 数据模型与接口建议（后续实现）

### 8.1 事实表/聚合表

建议保留现有小时聚合并增加可追溯维度：

- `performance_request_outcomes`：逻辑请求终态，一请求一行，保存请求模型、最终公司/模型、成功、重试恢复、最终延迟、TTFT、错误分类、终态覆盖来源。
- `performance_attempt_outcomes`：每次上游尝试一行，保存公司、渠道、模型、尝试序号、结果、耗时、错误类型、是否触达上游。
- `performance_hourly_rollups`：按 `bucket_start + company_id + group_id + requested_model + served_model` 聚合请求数、成功数、首次成功数、重试恢复数、尝试数、错误分类计数和可合并延迟分布。
- `performance_companies`、`performance_model_groups`、`performance_model_group_members`、`performance_slo_policies`：配置和版本。

如果复用现有 `perf_metrics`，必须明确它目前是请求边界的模型/分组小时聚合，不足以表达公司快照、首次失败、重试恢复、错误分类和可合并 P95；扩展前需要完成 SQLite、MySQL、PostgreSQL 的迁移、双次启动幂等和历史数据升级验证。

### 8.2 推荐接口

```text
GET  /api/performance-health/summary?from=&to=&company_id=&group_id=&model=
GET  /api/performance-health/timeseries?window=24h&bucket=1h&scope=site|company|group|model
GET  /api/performance-health/companies
POST /api/performance-health/companies
PATCH /api/performance-health/companies/:id
GET  /api/performance-health/companies/:id/groups
POST /api/performance-health/companies/:id/groups
PATCH /api/performance-health/groups/:id
GET  /api/performance-health/incidents?from=&to=&severity=
```

接口返回 `sample_count`、`terminal_coverage`、`data_freshness`、`window_start`、`window_end` 和 `definition_version`，前端不能仅凭 `success_rate = 0` 判断故障。指标定义版本变更时必须保留版本号，保证历史可解释。

## 9. 数据质量、异常与告警

页面必须单独展示：终态覆盖率、未知终态数、无公司归属数、无模型归属数、重复 request_id、聚合延迟、最近采集时间。数据不足时使用“未知/样本不足”，不使用伪造的 0% 或 100%。

建议首期可配置告警：

- 5 分钟窗口最终成功率低于 SLO 且样本数达到最小阈值；
- 连续 3 个小时桶低于 SLO；
- P95 最终延迟或 TTFT 超过阈值；
- 重试请求率或重试恢复率异常变化；
- 某公司/模型无数据但过去 24 小时有稳定流量；
- 数据新鲜度超过 5 分钟或终态覆盖率低于 99%。

告警需带公司、分组、模型、时间窗口、样本数、定义版本和下钻链接；同一异常在恢复前去重，避免每个重试发送一条告警。

## 10. 调研结论与指标依据

本需求参考了以下公开资料和 GitHub 项目：

- [Google SRE Availability Table](https://sre.google/sre-book/availability-table/)：可用性应使用聚合操作成功率，且要把可用性目标映射为错误预算。
- [Google SRE Service Best Practices](https://sre.google/sre-book/service-best-practices/)：SLI/SLO 与 error budget 用于平衡可靠性和变更风险。
- [OpenTelemetry HTTP metrics semantic conventions](https://opentelemetry.io/docs/specs/semconv/http/http-metrics/)：请求时长使用 histogram，错误类型作为维度，适合保留 P95/P99 和 error class。
- [OpenTelemetry GenAI metrics](https://github.com/open-telemetry/semantic-conventions/blob/main/docs/gen-ai/gen-ai-metrics.md)：建议记录 `gen_ai.client.operation.duration`、`gen_ai.client.token.usage`、TTFT、每个请求模型和响应模型。
- [OpenAI API latency troubleshooting](https://help.openai.com/en/articles/1000499-troubleshooting-api-errors-and-latency)：按模型区分错误比例、P50/P75/P95/P99、Request Time、TTFT 和 Token Velocity；这些指标应在模型详情中可切换查看。
- [Amazon Bedrock runtime metrics](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-runtime-metrics.html)：提供 InvocationLatency、客户端错误、限流、输入/输出 token 等 provider 侧维度，可作为适配层字段参考。
- [NVIDIA LLM API Gateway metrics](https://github.com/NVIDIA/nvcf/blob/main/docs/user/llm-gateway.md)：将入口请求、上游请求、上游耗时、token、TTFT、stream duration 分开，验证了“请求”和“尝试”双层事实的必要性。
- [LiteLLM Prometheus metrics](https://github.com/BerriAI/litellm-docs/blob/main/docs/proxy/prometheus.md)：将成功/失败 fallback、deployment state、每输出 token 延迟和限流分开统计。
- [mnfst/llm-gateway glossary](https://github.com/mnfst/llm-gateway/blob/main/docs/glossary.md)：明确区分 Request 与 Attempt；最终请求成功率与 attempt success rate 不能混为一个分母。
- [AI gateway benchmark](https://github.com/computesdk/benchmarks/blob/master/AI_GATEWAYS.md)：成功率必须包含超时、非 2xx、无内容流等失败，不能只看 HTTP 200；延迟、TTFT、吞吐与可靠性应联合解读。
- [openbenchmarks-labs/inference](https://github.com/openbenchmarks-labs/inference)：失败请求留在任务成功率分母，但不进入延迟分位数；p99 尾延迟、任务成功率和 tokens/s 要一起看。
- [AndrewTtofi/llm-gateway](https://github.com/AndrewTtofi/llm-gateway)：生产看板通常还需要 fallback rate、circuit breaker、upstream attempts、rejections、token/spend 和多窗口 burn-rate 告警。

由这些资料得到的设计选择是：用“最终请求成功率”作为用户体验主指标，用“尝试成功率/重试恢复率”解释路由行为；用 P50/P95/P99 和 TTFT 表示长尾；用 token、TPS、错误类型、数据覆盖率和错误预算避免单一成功率掩盖成本或质量风险。

## 11. 前端 demo 范围

demo 使用静态 fixture，不发送请求、不修改数据库、不改变真实导航权限。它应可展示：

- 24 小时总览与筛选控件；
- 总体、公司和模型 KPI；
- 成功率曲线、延迟曲线或切换；
- 公司健康排行和模型成功率排行；
- 重试恢复提示、样本量、数据新鲜度、未分组模型提示；
- 公司/模型分组配置入口的静态交互状态；
- loading、empty、低样本和错误状态的视觉占位。

demo 数据必须明确标注“示例数据”，不能让使用者误以为已经接入真实性能接口。

## 12. 验收标准

### 产品验收

- 管理员能在一个页面看到整站过去 24 小时最终请求成功率；失败后重试成功的请求只在逻辑请求分母中计一次且结果为成功。
- 能按公司、模型分组和模型筛选，并看到对应 24 小时曲线。
- 能分别看到最终成功率、首次成功率、重试请求率、重试恢复率、尝试成功率、P95 延迟和 P95 TTFT。
- 分模型成功率表支持字段显示/隐藏和排列顺序编辑，必选字段不能隐藏，刷新后能恢复已保存的视图偏好，并支持恢复默认配置。
- 无数据、样本不足、终态未知和数据延迟有明确状态，不能误显示为 0%。
- 管理员能维护公司、分组、模型成员和 SLO，并看到配置审计信息。

### 技术验收（真实实现阶段）

- 请求和尝试均可去重；多节点、重试、流式、异步任务不会重复计数。
- 延迟分位数来自可合并的原始分布，不从小时均值反推。
- 所有业务接口遵循项目 JSON wrapper、权限和 i18n 约定；前端复用现有 dashboard、table、chart、dialog 组件。
- 任何数据库/迁移变更完成 SQLite、MySQL、PostgreSQL 实例验证，覆盖新库、升级库和两次启动幂等。
- 有覆盖重试恢复、未知终态、空小时、低样本、无归属和权限拒绝的回归测试。

## 13. 后续值得继续观察的指标

首期看板稳定后，建议增加：模型/公司错误预算 burn rate、连续失败长度、熔断状态与恢复时间、供应商限流剩余额度、请求排队时间、流式中断率、schema/内容有效率、缓存命中率、输入/输出 token 成本、按用户组/地区/客户端版本的分层成功率、数据采集丢失率，以及在固定测试集上的离线质量/回归分数。离线质量分数必须与线上可靠性分开，不能把“回答错误”与“请求失败”混成一个成功率。
