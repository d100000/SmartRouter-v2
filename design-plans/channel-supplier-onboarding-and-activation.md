# 渠道商开户与渠道审核上线改造方案

状态为待实施。核对基线为 `5322773ff4094200722e925417d76d2b2083c30b` 及当前工作区中的渠道相关修改。

渠道商开户一次完成。平台默认开放其支持的供应商渠道模板和模型提交能力。渠道商提交并测试自有渠道，平台管理员选择实际对外提供的模型和分组、设置优先级与权重，并决定何时上线。每家渠道商使用一个专用平台账号，可以提交多条渠道。

## 现状与改造范围

- 「添加供应商」要求填写分组、允许的模板及模型，保存后还要去用户管理创建账号。当前的列表只提供到用户管理的通用跳转。见 `web/src/features/suppliers/components/supplier-editor.tsx:183`、`web/src/features/suppliers/lib/forms.ts:68`、`web/src/features/users/components/users-mutate-drawer.tsx:415`。
- 供应商保存渠道会触发后台测试，测试成功会立即写入在线配置及路由能力。供应商还可以暂停及恢复渠道、复制、丢弃和编辑限额。见 `controller/supplier.go:508`、`controller/supplier.go:1529`、`model/supplier.go:305`、`router/supplier-router.go:11`。
- 渠道分组当前来自供应商配置。管理员修改供应商配置或系统发布草稿时，都会把供应商分组写回旗下渠道。两条路径都需要改，管理员的逐渠道分组才能持续生效。见 `model/supplier.go:182`、`model/supplier.go:334`。
- 涉及管理员「渠道供应商」「用户管理」「渠道管理」和供应商工作台四个入口。平台自营渠道及渠道查看员继续走各自的既有流程。

## 产品决策

| 事项 | 渠道商 | 平台管理员 |
| --- | --- | --- |
| 开户 | 使用分配的专用账号登录 | 一次创建供应商及账号，管理登录和整家供货状态 |
| 渠道配置 | 提交自己的名称、模板、上游地址、凭据、模型和备注，可提交更新草稿 | 查看测试结果、关闭废弃草稿，按权限代提交 |
| 测试 | 在工作台发起测试，查看结果和失败原因 | 按权限测试，可查看待上线渠道 |
| 上线与流量 | 查看当前线上状态 | 发布指定版本、启停渠道、分配分组、设置渠道和供货池的优先级与权重 |
| 运营数据 | 查看当前状态及既有自有渠道的只读数据 | 管理渠道限额、供货池容量和采购设置 |

供应商的写操作限于提交渠道配置和测试，包括提交替换版本。供应商启停、复制、丢弃和改限额的入口与服务端权限一并撤销。账号安全功能沿用现有规则。管理员关闭整家供货时继续拦截正式流量和新的供应商探测，账号仍可登录查看。单条渠道处于待上线或管理员停用时，符合现有测试条件的探测仍可执行。

## 开户与默认供货范围

1. **渠道供应商页作为开户主入口。** 保留供货管理列表。「添加渠道供应商」默认填写供应商名称、登录用户名和初始密码。创建即绑定，返回供应商及用户 ID，刷新两个页面的数据。分组在渠道上线时设置，开户表单移除分组和裸用户 ID 输入。渠道数上限沿用平台现有默认值，供货池参数、采购成本倍率、Token 估算上界及可选范围限制收入高级设置。默认打开供应商供货许可，渠道仍需逐条上线。
2. **接入现有用户管理。** 用户管理列出同一条账号记录，支持按「渠道商」筛选及跳转对应的供应商记录。「新建用户」选择渠道商时进入同一开户流程。保留账号维护、密码重置及禁用登录能力。补齐 `web/src/routes/_authenticated/users/index.tsx` 对渠道商角色 `2` 的筛选参数。对已有未绑定账号的渠道商，供应商行提供「开通账号」。已有采购供应商可以使用原采购 ID 开通，历史渠道的管理归属仍按已有的明确归属处理。
3. **原子保存。** 在 `router/supplier-router.go`、`controller/supplier.go` 对接专用的开户操作，复用现有用户创建逻辑，包括 `User.InsertWithTx`、密码校验和首次改密。角色由服务端固定为供应商。在一笔事务中保存采购供应商、供货配置和用户绑定。用户名冲突、并发重复绑定或任一写入失败时回滚整笔事务。使用现有 `User.SupplierID` 唯一索引限制一户一账号。事务成功后发布账号和供应商状态并记录审计。两个入口及历史绑定路径都遵守现有角色和操作权限。
4. **默认可提交全部支持项。** 新供应商的模板、模型可分别使用「全部平台支持」范围，供应商创建表单无需选择。在 `SupplierAccount` 增加 `allow_all_templates` 和 `allow_all_models` 两个标记，由开户逻辑设置为开启。存量非空白名单继续生效，管理员可主动切换。编辑时省略范围字段则保留原值，明确选择「全部」才解除限制。迁移不把缺失或损坏的配置视为授权。
5. **保持模板与测试边界。** 改动覆盖 `model/supplier.go` 的权限判断、`controller/supplier.go` 的账户保存及模板返回、供应商和管理员共用的模板筛选。普通模板支持填写实际模型名，固定目录的模板遵从自身声明。渠道提交时仍填写至少一个实际模型。模板以 `service/supplier_templates.go` 中可供供应商使用的目录为准。未支持的模板、未注册插件和不满足模板约束的模型继续拒绝。允许先提交名称合法的模型，测试缺少平台模型配置、计价或预算条件时显示具体待处理原因，补齐后再测试。

## 渠道从测试到上线

| 动作 | 工作台显示 | 正式流量 |
| --- | --- | --- |
| 上传新渠道或替换配置 | 待测试 | 新渠道不接流量，原渠道沿用线上版本 |
| 发起测试 | 测试中或等待上游结果 | 无变化 |
| 测试结束 | 测试失败，或测试通过 · 待上线 | 无变化 |
| 管理员确认上线 | 已上线，显示管理员选定的分组 | 以审核通过的版本和分组参与路由 |
| 管理员关闭废弃草稿 | 草稿已关闭，仍可查历史 | 已有线上版本继续运行 |
| 管理员关闭渠道或移除分组 | 已停用，或更新已启用分组 | 停止该渠道或该分组接收新流量 |

1. **草稿和线上版本分开。** 修改 `model/supplier.go` 的 `SaveSupplierChannelDraft`。新渠道明确处于未上线状态，无线上模型或可用能力记录，也不把默认分组用于正式路由。保留 `SupplierValidated` 表示已有正式发布的配置，`Channel.Status` 表示正式渠道的运行状态。供应商提交旧渠道的更新时，只更新草稿和草稿版本，线上地址、凭据、模型、名称、分组、限额及调度设置保留。旧供应商停用标志交由管理员在有权恢复时显式处理。
2. **提交和测试是独立操作。** 上传只保存草稿。复用 `TestSupplierChannel`、探测租约及异步结果轮询。测试在现有隔离路径中运行，必要的测试分组由服务器提供，继续执行 HTTPS、上游目标验证、凭据只写、测试限流及采购预算规则。供应商重测已发布的配置时，只产生诊断结果。新的草稿版本必须与测试结果对应。
3. **测试只记录结果。** 在 `controller/supplier.go` 的验证任务中移除自动发布。将通过的模型集合写入对应草稿版本的 `tested_models` 文本字段，并设置「测试通过 · 待上线」。模型沿用各协议现有的通过条件，部分成功时管理员只能选择实际通过的模型。测试失败、异步结果未知和旧版本的迟到结果都不能推动发布。重测同一草稿时使用现有任务归属与状态锁，防止重复付费探测或复用失效结果。
4. **管理员显式发布。** 在现有渠道管理列表和卡片提供「审核上线」或「发布更新」。确认页展示供应商、草稿版本、提交及通过的模型、当前线上配置摘要。管理员选择至少一个有效的渠道分组和通过测试的模型，填写适用于该渠道的优先级和权重。更新已上线渠道时预填线上值。首次上线、发布更新和恢复停用渠道分别操作。发布更新时，已经停用的渠道保持停用，管理员恢复后才重新接流量。
5. **发布时一次提交。** 提供管理员草稿发布接口，例如 `POST /api/suppliers/channels/:id/publish`，请求携带草稿版本、选中的模型、分组、渠道优先级及权重。校验所需的启停、路由设置及凭据发布权限，并对敏感发布执行现有机制的操作验证。事务内锁定供应商、渠道与草稿，重查待上线状态、版本、模板能力、可用模型、分组和当前正式状态。管理员看到的配置已变更时提示刷新。复用 `PublishSupplierChannelDraft` 的凭据绑定和能力更新逻辑，原子写入所选配置及路由能力。事务成功后同步渠道缓存、调度快照和前端查询。重复确认和并发更新不会发布两次。
6. **分组和调度由管理员持有。** 取消新渠道正式分组对供应商分组的继承，移除更新供应商或发布草稿时的覆盖行为。渠道分组选中后，该渠道上线时才会服务这些分组，移除某一分组只撤回其对应的路由能力。管理员编辑渠道时控制调度实际消费的字段。当前供应商内调度读取 `SupplierPriority` 和渠道权重，供货池读取 `PoolPriority` 和 `PoolWeight`。在界面上标注两者的适用范围，并覆盖普通选路及智能调度验证。见 `service/scheduler_routing.go:70`、`service/supplier_routing.go:31`。
7. **堵住常规启用入口的旁路。** 供应商上传接口仅接受草稿字段，服务器拒绝状态、分组、优先级、权重、限额和代填归属。检查管理员的单条、批量、按标签启用、通用编辑、自动恢复、能力修复以及缓存和绑定渠道路径。所有路径都必须保证未发布的供应商渠道不可用于正式调用。已发布渠道继续接受既有健康检查和管理员启停逻辑。相关入口见 `router/supplier-router.go`、`router/channel-router.go:78`、`model/channel.go:1188`、`model/ability.go:386`。
8. **管理员关闭废弃草稿。** 在渠道管理提供「关闭草稿」，由服务端校验权限和当前草稿版本。已有探测任务时，待其结束后再关闭。关闭从未上线的草稿后释放一个渠道名额，保留渠道 ID、测试记录与审计，供应商不能重新编辑或测试该草稿。关闭已上线渠道的更新草稿时，当前线上版本、名额和历史保留，供应商仍可提交新的更新版本。关闭、测试和发布走同一套版本和状态检查，避免迟到结果重新开放已关闭草稿。普通停用渠道清理跳过供应商草稿，其他渠道照常清理。现有计数与删除限制见 `model/supplier.go:228`、`model/channel.go:984`、`model/channel.go:1439`。

供应商接口继续用 `POST /api/supplier/channels` 上传、`PUT /api/supplier/channels/:id` 提交更新、`POST /api/supplier/channels/:id/test` 测试指定版本。列表和详情返回草稿版本、测试状态、通过的模型及是否已有线上配置。管理员列表同时读取正式启用状态和草稿待上线状态。响应只提供脱敏配置和凭据已设置状态。

## 存量兼容与上线顺序

1. **先就绪服务端和数据。** 扩展范围模式和草稿的测试结果存储，沿用现有供应商、渠道、凭据及用户主键。已发布渠道保留当前状态、分组、优先级、权重、历史归属和限额。未发布的旧草稿进入待测试或继续已开始的测试。旧草稿已经启动的异步探测保留任务 ID 和租约，重启后继续收结果。供应商限制名单维持原值，历史未绑定账号的记录走原地开通。线上配置和更新草稿并存时，保留线上配置及对应的历史，不能拿最新草稿版本推断过去已经发布了什么。
2. **切掉旧自动发布方可开放新提交。** 切换时暂停供应商写入和旧验证任务，等待在跑的旧版本验证退出，再启动新版后台任务及界面。旧版验证进程会把测试成功写成正式配置，旧节点继续接管草稿会破坏新流程。正式流量继续按现有配置运行。回滚时先停新版本写入并隔离新版未审核草稿，再恢复旧服务；如果旧版自动发布仍可能触达这些草稿，保留旧验证任务停用并修正后再开放。
3. **最后启用新表单和审核入口。** 先确认管理员能审查和上线，再恢复渠道商提交。观察待测试、待上线、权限拒绝和发布冲突状态，确认已上线渠道未出现分组漂移或流量中断。将现有 [渠道供应商产品规划](channel-supplier-role-product-plan.md) 中关于自动上线、供应商调度权限、组继承和开户的冲突段落列入实施后的文档同步。

## 验收与实施检查

| 验收项 | 通过标准 |
| --- | --- |
| 一次开户 | 不选分组、模板和模型也能保存。用户管理立即查到唯一专用账号。重复用户名或并发开通产生明确冲突，数据库中无半成品。关联已有采购记录时旧渠道归属不变。 |
| 提交范围 | 新账号可提交平台支持的模板及实际模型。旧非空白名单仍有效，显式切换到全部后生效。固定目录、模板与模型校验、秘密保护继续通过。 |
| 权限 | 渠道商能提交、更新草稿和测试自己的渠道。跨供应商请求、直接访问旧的启停、复制、删除、限额修改操作或提交管理字段都被服务器拒绝。只有符合权限要求的管理员能开户、发布、启停和调权。 |
| 审核上线 | 测试通过且未审核时，没有正式流量。上线后只在所选模型及分组可调度。管理方移除分组后该分组立即失去该渠道。修改该供应商的其他设置时，渠道分组维持原值。 |
| 草稿关闭 | 管理员关闭从未上线的草稿后，供应商可使用释放的名额提交新渠道，原测试记录仍可查。关闭更新草稿后，原渠道继续运行且名额不变。供应商直接调用关闭接口、关闭后发布旧草稿及并发测试均不能改变已关闭状态。 |
| 并发与恢复 | 草稿更新后旧版本测试和审核无法发布。替换草稿测试、线上配置停用、批量启用或能力修复期间没有提前接流量。部分通过、任务等待、重启及失败恢复均能得出正确结果。 |
| 存量路由 | 升级后已启用、管理员停用和原供应商已暂停的渠道维持各自有效状态，在线模型、分组、凭据绑定、限额历史和调度权重可核对。 |
