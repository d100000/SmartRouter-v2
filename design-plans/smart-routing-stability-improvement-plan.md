# 智能路由稳定性改进方案

目标：多渠道下稳定分发。具体指：单个渠道故障时，客户端可见失败和额外延迟尽量少；正常时流量按健康度和容量分散；会话粘性在不牺牲可用性的前提下保持，以提高提示缓存命中。

本方案基于对 `pkg/scheduler/`、`service/channel_select.go`、`service/scheduler_routing.go`、`service/scheduling_config.go`、`middleware/distributor.go`、`controller/relay.go` 的审查。每个问题标注证据等级：

- **已复现**：用真实中间件或引擎跑过用例。
- **代码确认**：读代码确认，未写用例。
- **待验证**：推断，落地前需先补用例或数据。

## 三、阶段 0：粘性

### 目标

- 智能路由是否激活，都先用绑定渠道（工作区已完成）。
- 只有请求最终成功才写回。
- 粘性不因回退而改变：绑定渠道满载、冷却或未通过健康门槛时，这次请求可以临时走别的渠道，但绑定始终保持原渠道，没有"连续回退若干次后改绑"。
- 只有绑定渠道真正派发失败、重试到其他渠道成功时，才按切换开关决定是否改绑。
- 改绑之后不再回退：会话从 A 改绑到 B 后，A 恢复也不会自动回到 A。之后只有 B 自己真正派发失败、重试成功时才会再次改绑，目标是这次实际成功的渠道。

### 行为规则

| 场景 | 是否写回 | 写回到 |
| --- | --- | --- |
| 绑定渠道 A 成功 | 是（刷新 TTL） | A |
| A 冷却中，回退到 B 成功 | 否 | 保持 A |
| A 满载，回退到 B 成功 | 否 | 保持 A |
| A 健康门槛未通过（阶段 2 引入），回退到 B 成功 | 否 | 保持 A |
| A 实际派发失败，重试 B 成功 | 是 | `SwitchOnSuccess` 开：B；关：A |
| 无绑定，新会话首次请求成功 | 是 | 实际成功的渠道 |
| 流式请求已写出内容，最终失败 | 否 | — |
| 所有尝试失败 | 否 | — |
| 已从 A 改绑到 B，A 恢复，B 成功 | 是（刷新 TTL） | B（不回到 A） |
| 已改绑到 B，B 冷却或满载，临时走 C 成功 | 否 | 保持 B |

已知代价：A 持续满载期间，同一会话每次请求都先试 A、被拒、重新抽签，可能每次落到不同渠道，这段时间缓存命中会下降。A 恢复后会话立即回到 A。阶段 1A 把默认容量改为不限后，只有管理员显式设置了容量的渠道才会出现持续满载。

### 实现要点

- `service/channel_select.go` 的 `reserveAffinityChannel`：临时性回退时，在请求上下文记录"绑定被保留"标记和回退原因。
- 记录回退次数（按分组、模型计数），用于观测粘性被临时绕开的频率，不影响绑定。
- `middleware/distributor.go`：写回条件从 `Writer.Status() < 400` 改为 `RequestPolicy(c).Successful`。该字段已按流式最终结果计算（`MarkRequestPolicySuccess`）。
- `service/channel_affinity.go` 的 `RecordChannelAffinity`：读取"绑定被保留"标记，命中时不写回。
- `relay/responses_websocket.go`：WebSocket 在上游接受请求时写回，语义不同于 HTTP（一个连接多次调用），本阶段不改，在文档中注明。

### 测试与验收

- 扩展 `service/channel_select_auto_groups_test.go` 现有的粘性表格测试，用真实 `Distribute()` 中间件覆盖上表每一行，`SwitchOnSuccess` 开、关各一次。
- 连续多次满载回退后，绑定仍是 A；A 释放名额后，下一次请求选 A。
- A 派发失败、重试 B 成功后，绑定为 B；随后 A 恢复健康，同一会话后续请求仍选 B。
- 验收：A 短暂满载或冷却后恢复，同一会话下一次请求回到 A。

## 四、阶段 1A：容量

### 目标

未配置容量时不限并发，保留管理员和供应商的显式限额；区分"候选已满但请求去了别处"和"请求因容量耗尽返回 503"。

### 行为变更

- 容量 0 或空表示不限。`scheduler.DefaultConfig().DefaultCapacity` 改为 0。
- 共享池规则不变（取成员最小正值），不限的成员自然不参与取最小值，所以 P4 随之解决。
- 负载权重继续生效：容量为 0 时引擎按 100 作分母计算在途惩罚（`scoring.go` 已有逻辑），流量仍会避开在途多的渠道。
- 供应商池：`PoolCapacity` 为 0 时目前也会落到默认 100，同样改为不限。

### 存量配置迁移（已定：一次性迁移为不限）

已保存的配置把当时的默认值 100 作为显式值存进了 `SchedulingConfig`，无法区分"管理员选了 100"和"默认值"。处理方式：

- 在 options 中加 `SchedulingConfigVersion`。启动或同步配置时，版本从 1 升到 2，把所有 `default_capacity == 100` 改为 0（不限），写回后版本记为 2，之后不再执行。
- 渠道容量覆盖和供应商池容量里的显式值不动，只改分组、模型的默认容量。
- 记一条管理日志，列出被改的分组、模型，管理员确实需要 100 时可按日志改回。
- 多实例同时启动时，迁移结果相同（只把 100 改为 0），重复执行不会出错。

### 实现要点

- 后端校验：`default_capacity` 和渠道容量覆盖允许 0 或空，上限仍为 100000。
- 前端 `web/src/features/scheduling/components/config-dialog.tsx`：容量输入框允许留空，留空显示"不限"；新增文案补齐 7 种语言。
- 可观测性：
  - 引擎计数两类事件：`capacity_skipped`（选路时某候选因满被排除，但请求选到了别的渠道）和 `capacity_exhausted`（所有候选都满，返回 503）。
  - `capacity_exhausted` 每个分组、模型每分钟最多一条警告日志。
  - 快照的 `Summary` 加两个 30 分钟计数，看板健康概览展示。

### 测试与验收

- 引擎：容量 0 时 250 个并发全部准入；一个成员 20、一个成员 0 时，生效容量为 20；不限时在途多的渠道权重下降。
- 迁移：在 SQLite、MySQL、PostgreSQL 三种真实数据库上跑 `TestSchedulingDatabaseMatrix`，覆盖迁移一次和重复启动两次的结果。
- 验收：未配置容量的站点，高并发流式请求不再出现容量 503。

## 五、阶段 1B：元数据重建

### 目标

重建移出请求路径；读库失败不影响选路；内容没变不触发重建。

### 实现要点

1. **先修基础缓存**（`model/channel_cache.go` 的 `InitChannelCache`）：两次 `DB.Find` 检查错误，失败时记录错误、保留旧缓存、不让版本加一，直接返回。
2. **内容没变不加版本**：定时刷新时对参与路由的字段算一个指纹（渠道 ID、状态、分组、模型、优先级、权重、供应商归属，以及能力表的启用状态），与上次相同就不调用 `invalidateRoutingMetadata()`。渠道增删改等其他调用点保持原样。
3. **后台重建**（`service/scheduling_config.go`）：
   - 请求路径只比较版本号。已有成员关系时，发现版本变了就非阻塞地通知后台协程（容量为 1 的通道，自然合并重复通知），本次继续用旧数据。
   - 后台协程在锁外读库并计算渠道层和供应商层的完整成员关系，算完后短暂加锁一次发布两层结果，保证两层一致。
   - 失败时保留上一份，按 1、2、4 秒退避，最长 30 秒，记录错误日志。
4. **保持同步的两处**：进程启动后的第一次构建；`SaveSchedulingConfig`（管理员保存后要立即生效并返回结果）。
5. **禁用和撤销的及时性**：候选列表来自渠道缓存，缓存刷新后禁用立即生效；粘性和固定渠道在 `ReserveSchedulingChannel` 中重新读取最新状态。需要补一处：引擎为不在当前能力表里的固定渠道保存的 `channelMetadata` 状态，在重建前可能过时，导致宿主刚确认启用的渠道被旧状态拒绝；预留时应以宿主传入的最新状态为准。供应商凭据撤销走的是 `invalidateRoutingMetadata()`，要确认撤销后的第一次派发前已有宿主侧校验，否则对撤销保留同步重建。

后续可选：开启内存缓存时，重建直接使用渠道缓存里的数据而不再读库。前提是渠道缓存也持有能力表的启用状态，目前没有，暂不做。

### 测试与验收

- 渠道内容没变时定时刷新，版本不变、不触发重建。
- 重建期间调度读库失败：选路继续用旧数据成功，恢复后自动重建。
- 基础缓存读库失败：缓存保持旧数据。
- 禁用渠道后，在后台重建完成前，新请求不会派发到它。
- 本阶段改了读库路径的错误处理，按 AGENTS.md 要求在三种真实数据库上运行现有调度数据库矩阵测试。
- 验收：在 1 万行能力表的环境下，用锁剖析确认请求路径上不再出现整表读库。

## 六、阶段 2：冷却与粘性健康门槛

### 目标

整个渠道故障时快速挡住，同时避免一个有问题的请求把所有渠道都冷却掉。

### 行为变更

1. **扩大触发范围**：可归因于上游的失败都推进连续失败计数，包括 5xx（含 500）、连接失败、429、流中断（超时、读取错误）。客户端取消、参数错误、本地拒绝已经被分类为"忽略"，不受影响。
2. **只有成功清零**：认证失败这类不触发冷却的渠道失败，既不推进也不清零计数（目前会清零）。
3. **按不同原始请求计数**：连续失败必须来自不同的原始请求，同一个请求的多次重试不重复推进。这防止一个必然失败的请求在低流量时冷却所有渠道。
4. **最后一个可用渠道保护**：冷却会让该分组、模型没有任何可用渠道时，不进入冷却，只记录告警。
5. **退避**：第一次冷却 15 秒，此后每次连续冷却翻倍，上限 5 分钟；成功一次后重置。
6. **半开探测**：冷却到期后同一时刻只放 1 个请求，成功后完全恢复，失败则进入下一档冷却。
7. **渠道级冷却**：同一渠道 1 分钟内在 2 个以上模型维度进入冷却时，整条渠道在所有维度冷却基础时长。按模型的冷却保持不变，因为常见故障只影响某一个模型。
8. **粘性健康门槛**（prefer）：绑定渠道最近 60 秒有可冷却失败，且有健康的替代渠道时，跳过绑定、正常选路。按阶段 0 规则视为临时回退，不立即改绑。strict 和固定渠道不受影响。

### 调度中心页面展示

分组页签的渠道明细里，处于冷却的渠道显示：

- **冷却时间**：开始时间、本次冷却时长（当前退避档位，例如"第 3 档，60 秒"）和剩余秒数。渠道级冷却单独标注。
- **冷却期间的请求次数**：冷却开始以来，本应参与选路、因冷却被跳过的请求数。
- **半开探测**：冷却到期后放进去的探测请求，显示次数和结果（成功恢复 / 失败进入下一档）。
- 冷却结束后，在当前 30 分钟窗口内保留最近一次冷却的开始时间、总时长和期间跳过的请求数，便于事后排查。

实现：引擎在冷却状态里记录开始时间、档位、跳过次数和探测结果，`ChannelSnapshot` 增加对应字段（已有的 `CooldownUntil` 保留）；前端在 `web/src/features/scheduling/components/channel-table.tsx` 的"当前路由状态"列展示，剩余时间随页面 15 秒刷新更新；新增文案补齐 7 种语言。

### 实现要点

- `service/scheduler_routing.go` 的 `FinishSchedulingAttempt`：重新定义 `CooldownFailure`。
- `pkg/scheduler/engine.go`：连续失败状态记录最近失败的请求 ID；增加退避档位、半开探测位、渠道级冷却表；`finishAttempt` 在决定冷却前检查其他可用成员。
- 引擎新增 `BindingAdvisable(key, channelID) bool`，供 `reserveAffinityChannel` 调用。
- 更新 `SCHEDULING.md` 第 3.5 节和第 4 节关于冷却的描述。

### 测试与验收

- 引擎表格测试：500 连续 3 次触发冷却；500 与 503 交替也触发；同一请求的 3 次重试不触发；唯一可用渠道不冷却；退避 15、30、60 秒到 5 分钟上限；半开期间第 2 个并发请求被排除；两个模型同时冷却触发渠道级冷却。
- 重跑本次的引擎模拟（2 渠道、每秒 5 个请求、A 故障 3 分钟）：500 场景的首次失败率从 32.8% 降到与 503 场景相当（约 4%）。
- 粘性：绑定渠道刚出现可冷却失败时，下一次请求跳过它且不改绑。
- 页面：冷却中的渠道显示开始时间、时长、剩余时间和期间跳过的请求数；冷却期间每被跳过一次计数加一，半开探测单独计数；前端测试覆盖冷却中、半开、刚结束三种状态。

## 七、阶段 3：本地拒绝后的选路

### 目标

本地准入拒绝（如超过渠道限额）只排除该渠道，不把下一次选路当成重试。

### 实现要点

- `service/scheduler_routing.go` 的 `schedulerSelectChannel`：传给引擎的重试标记目前是 `retry > 0 || len(use_channel) > 0`，改为"本请求已有尝试真正发往上游"。已派发次数在 `StartSchedulingAttempt` 中记录。
- 排除集合不变：本地拒绝过的渠道仍通过 `use_channel` 排除。

### 测试与验收

- 激活状态下，第一个渠道被本地拒绝后，下一次选路按概率抽签而不是取最高权重（固定随机数验证）。
- 真正派发失败后的重试仍按权重排序。

## 八、阶段 4：重试是否随机化（实验）

当前按含实时负载的最高权重排序，符合 `SCHEDULING.md` 的约定。只有数据证明有害才改。

- 用引擎模拟 3、4、5 个渠道，一个渠道故障，对比"按权重排序"和"按权重随机"两种重试策略。
- 指标：重试流量在单个渠道上的最大占比、最终成功率、按模拟延迟算的 P95。
- 判定：随机策略在不降低最终成功率的前提下，把重试最大占比降低 20 个百分点以上，才改为默认。

## 九、上线与观测

- 每个阶段单独发布，按阶段 0 → 1A/1B → 2 → 3 的顺序。阶段 2 改动最大，先在一个低流量分组观察一天。
- 每个 PR 同步更新 `SCHEDULING.md` 中对应的行为描述。
- 发布后关注：
  - 粘性：绑定命中率、改绑次数、临时回退次数。
  - 容量：`capacity_exhausted` 计数应为 0（未配置容量时）。
  - 重建：重建次数应明显下降（渠道无变化时为 0），重建失败日志。
  - 冷却：冷却触发次数、渠道级冷却次数、"最后一个渠道不冷却"告警次数、故障期间的首次失败率。

## 十、已定事项

1. 存量配置里的 `default_capacity == 100` 一次性迁移为不限。
2. 粘性不因临时回退改绑，只有真正派发失败后重试成功，才按切换开关改绑。
3. 冷却参数：起始 15 秒、翻倍、上限 5 分钟，到期后半开只放 1 个请求。长时间故障时，自动禁用规则仍按原逻辑禁用渠道。
4. 调度中心页面展示冷却时间和冷却期间被跳过的请求次数。
